# [ADR-0016] AML ポリシーのバージョン付き YAML 表現

| 項目 | 内容 |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-07 |
| 関連ADR | ADR-0004, ADR-0012 |

## コンテキスト

「Configuration as the Product」を掲げながら、規制判断の中核が Go のコードに埋まっていた。

- 取引時確認で顧客タイプごとに何を取得すべきか（DR-13）はどこにも表現されておらず、
  `isValidCustomerType` は 8 タイプを受け入れるのにエラーメッセージは 3 タイプしか挙げず、
  残り 5 タイプは本人確認要件ゼロで通っていた
- EDD の 30/60/90 日という段階スケジュール（DR-14）は調査画面のリテラル、エスカレーション
  ジョブ、プロセス設定の 3 箇所に重複していた。3 者が食い違えば、画面が「期限内」と表示する
  顧客をジョブがエスカレーションする
- どの CDD ルールセットが顧客に適用されるか（DR-15）は表現されておらず、UI は
  「API が最初に返したもの」を使っていた。適用可否が一覧エンドポイントの並び順という偶然に
  依存していた
- トラベルルールの適用判定（DR-16）は `content/` に一切存在せず（"travel" の grep ヒット 0）、
  クライアントの主張をそのまま採用していた
- スクリーニングのソース一覧と 72 時間の鮮度閾値はサーバーコードの定数だった

## 決定

`api/internal/policy/` に 5 つのポリシー文書を置き、対応する `content/*_v1.yaml` を同梱する。
形は `casemgmt.PriorityPolicy` に完全に従う: 固定の `schema_version`、必須の `policy_version`、
コード内 `Default*()`、空パスで既定を返す `Load*(path)`、engine が解釈できない文書を拒否する
`Validate()`、そして digest。

| ポリシー | 解決する問題 |
|---|---|
| `kyc_required_fields_v1` | DR-13。8 つの `domain.CustomerType` すべてが解決可能であることを `Validate()` が強制する |
| `edd_policy_v1` | DR-14。段階スケジュールの唯一の出典 |
| `cdd_rule_selection_v1` | DR-15。適用可否を宣言的なマッチ規則にする |
| `travel_rule_v1` | DR-16。ADR-0017 参照 |
| `screening_readiness_v1` | DR-09。ソース一覧、ソースごとの鮮度窓、未 import の許容可否 |

`policy.Set` は **nil レシーバを許容**する。`s.policies.KYC()` は nil のときコード内既定値を返す。

読み取り専用の `GET /api/v1/policies` と `GET /api/v1/policies/{policy}` を公開し、UI は
これ経由でのみ参照する。ポリシー値を画面にハードコードしない。

`casemgmt.PriorityPolicy` は `policy` パッケージに**移さない**。

## 根拠

nil 許容は設計上の中心である。これがないと、ポリシーを組み立てていない既存の httptest
約 200 本がすべて改修対象になり、Wave 3 の作業がテスト書き換えに食われる。既定値がコードに
あることは「設定ファイルがなければ動かない」を避けるためでもある: 単一テナントの導入で
YAML を 5 本置くことを前提にしない。

digest は既存経路で `batch_runs.config_digests` / `screening_runs.config_digests` まで流れる。
どの判断がどのポリシー版で下されたかが、判断そのものと同じ行に残る。

JSON Schema は `travel_rule_v1` と `kyc_required_fields_v1` の 2 本のみ作った。
`content/schema/*.json` は `website/scripts/generate-schema-docs.mjs` が拾って docs ページを
自動生成し、en/ja 両方のロケール登録と `content/README.md` の行追加を要求する。規制面で運用者が
手編集する可能性が最も高い 2 本に絞った。前例の `content/case_priority_v1.yaml` も
JSON Schema を持たない。

`casemgmt.PriorityPolicy` を動かさないのは、動作していてテスト済みだからである。移動すれば
無関係なファイルが差分に現れ、レビューが「本当に何も変わっていないか」の確認に費やされる。
新しいポリシーが同じ形に従うことで、将来 1 箇所に集約する余地は残る。

## 棄却した代替案

**環境変数の拡張。** `MERLON_EDD_STAGE2_DAYS` の路線を全ポリシーに広げる案。顧客タイプ別の
必須項目のような構造を環境変数で表現できない。既存の 2 変数は互換のため残し、ポリシー
ファイルがあればファイルが勝ち、env が非既定値なら起動時に警告する。

**データベーステーブル。** ポリシーを行として持つ案。ポリシーはコードと同じ頻度でレビューされ、
同じようにバージョン管理されるべきもので、運用中に UI から書き換わるものではない。

## 影響

規制要件の変更が、Go の変更ではなく YAML の変更になる。何が要求されているかを、コードを
読まずに読める。

代償として、ポリシーとコードの二重管理が生まれる。同梱 YAML とコード内既定値が食い違わない
ことを digest 一致テストで担保しているが、これは新しいポリシーを足すたびに書く必要がある。
