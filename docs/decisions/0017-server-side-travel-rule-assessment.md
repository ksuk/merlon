# [ADR-0017] トラベルルール適用判定のサーバー側決定

| 項目 | 内容 |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-07 |
| 関連ADR | ADR-0016 |

## コンテキスト

`transactions.travel_rule_applicable` はクライアントの主張をそのまま採用していた。さらに
counterparty ブロックを持たない取引ではこの値が永久に NULL のままで、UI はそれを「legacy」と
表示していた。結果として、**評価されたことのない取引と、フィールド導入前の取引が区別できない**。
金融機関が「自分の取引のどれがトラベルルール評価を受けたか」を答えられない状態だった。

`travel_rule_evidence` は無検証で、`travel_rule_status: complete` を主張しながら必須項目が
欠けている取引がそのまま保存できた。適用除外の理由は自由文字列で、書籍全体に対して
「なぜ除外したのか」を集計できなかった。

## 決定

すべての取引について、サーバーが `travel_rule_v1` ポリシーに照らして適用判定を計算し、
`transactions.travel_rule_assessment` (JSONB) に永続化する。記録するのは
`{policy_version, applicable, reason_code, missing_fields, threshold, currency, conflict, evaluated_at}`。

閾値は**暗号資産チャネルで 100,000 JPY 相当以上**（閾値ちょうどを含む）。

**矛盾時**: `assertion_authority: client` を既定とし、クライアントの `travel_rule_applicable` は
**上書きしない**。食い違ったら両方を保持し、`conflict: true` を記録して `Warning: 299` を返す。

**金額換算**: FX 概念を持ち込まない。閾値通貨と一致すればその額、異なれば**閾値以上として扱う**。

**evidence 検証**: `travel_rule_status == complete` を主張しながら
`required_evidence_fields[counterparty_type]` に欠損があれば、欠損項目名を挙げて 400。

**理由コード**: 閉じた enum の `travel_rule_not_applicable_reason_code` を新設。自由文の既存
フィールドは受け続け、コードなしの自由文は `other` にマップする。

**incomplete の扱い**: 適用対象だが必須 evidence が未着の取引は、201 で受理したうえで
`travel_rule_incomplete` 理由の PENDING_REVIEW に積む。

既存行はバックフィルしない。

## 根拠

クライアント権威を既定にしたのは、サーバー判定が既存の申告と食い違ったときに 400 で拒否すると、
移行期間中に基幹システムからの取引が入らなくなるからである。「金融機関はこう申告し、設定された
ポリシーはこう含意する」という不一致そのものが、レビュアーが見るべき所見である。ポリシーを
`assertion_authority: server` に切り替えれば将来ハード 400 にできる。

FX を持ち込まないのは、誤ったレートが「自信を持った誤答」を生むからである。比較できない金額は
Fail-Alert に従って「該当しうる」として扱い、レビュアーの目に触れさせる。黙って除外扱いに
するより良い。

incomplete を 400 にしないのは、**取引は実際に起きた**からである。記録を拒否しても取引は
消えない。コンプライアンス上の不足は、記録の拒絶理由ではなく作業項目である。

バックフィルしないのは、過去の取引を今日のポリシーで評価すると、当時誰も下していない判断を
捏造することになるからである。NULL は「not applicable」でも「unknown」でもなく「評価されていない」
であり、UI はこの 3 つを区別して描画する。

## 棄却した代替案

**サーバー権威を既定にする。** 移行期間の取り込み停止リスクが大きい。設定 1 行で切り替えられる
形にして、金融機関の判断に委ねた。

**適用判定をエンジンに置く。** エンジンは取引監視のシナリオ評価を担い、法域固有の規制閾値は
運用者が編集する設定である。ADR-0016 の分割に従った。

## 影響

「この取引はトラベルルール評価を受けたか」に、取引行だけで答えられるようになる。conflict と
incomplete がそれぞれ独立に集計できる。

代償として、取引作成のたびにポリシー評価が走る。判定は純粋関数で I/O を伴わないため実測上の
影響はないが、取引作成のホットパスに規制ロジックが乗ったことは記録しておく。
