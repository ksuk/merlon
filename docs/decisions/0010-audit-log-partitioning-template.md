# [ADR-0010] 監査ログ・取引テーブルのパーティショニングはテンプレート提供に留める

| 項目 | 内容 |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-07-06 |
| 関連ADR | なし |

## コンテキスト

`audit_logs`（RET-002：10年保持）と `transactions`（7年保持）は、運用が長期化するほど行数が増え続け、単一テーブルのままでは保持期間超過データの自動パージ（RET-003）や範囲検索のコストが増大する。PostgreSQL の宣言的パーティショニング（`PARTITION BY RANGE`）は、この種のテーブルに対する標準的な対処である。

一方で、Merlon は既に稼働中の導入先が存在し得る自己ホスト型ソフトウェアであり、非パーティションテーブルをパーティションテーブルへ変換する操作は「新しいパーティション済みテーブルを作成し、全データを移行し、参照を切り替える」という破壊的かつダウンタイムを伴う移行を要する。これは `03_implementation-plan.md` の Global Constraints が定める「migrations は additive のみ」の原則に反する。

## 決定

- 本リポジトリのマイグレーション（`migrations/*.sql`）としては、既存の `audit_logs`/`transactions` テーブルをパーティション化する変更を**行わない**。
- 代わりに、新規導入企業がゼロから環境を構築する際に採用できる月次 RANGE パーティションの DDL テンプレートを `docs/compliance/data-retention.md` に例示として掲載する。
- 既に稼働中で非パーティション運用のテーブルをパーティション化したい導入企業向けには、一般的な移行手順（新テーブル作成→並行書き込み→データ移行→切替）の概要のみを案内し、本リポジトリの自動マイグレーションとしては提供しない。

## 根拠

- 既存テーブルへの後付けパーティション化はダウンタイムまたは二重書き込み期間を要する運用上重い作業であり、`make test`/`make build` の対象である自動マイグレーションに含めると、稼働中の導入先で意図せず実行されるリスクがある。
- 一方で新規導入企業にとっては、最初からパーティション構成で始める方が将来のコストを大きく下げるため、テンプレートとして提供する価値は大きい。
- RET-002 の保持期間（監査ログ10年、その他7年）とRET-003の自動パージは、パーティション有無に関わらず `retention_policies` テーブルと `PurgeJob`（`api/internal/retention/purge.go`）で機能するため、パーティショニングの有無はコア機能の前提条件ではない。

## 棄却した代替案

- **本リポジトリのマイグレーションとして既存テーブルを強制的にパーティション化する** — additive 原則に反し、稼働中導入先のデータ移行を無条件に強制することになり危険すぎるため却下。
- **パーティショニングを一切文書化しない** — 大量データを扱う導入企業が独自に設計する際の指針を欠き、保持期間・パージ運用の実装意図（監査ログのみ10年、他は7年で延長のみ可）との整合を取りにくくなるため却下。

## 影響

- `docs/compliance/data-retention.md` の「アーカイブ戦略」節を、新規導入企業向け DDL テンプレート例（`audit_logs`/`transactions` の月次 RANGE パーティション `CREATE TABLE` 文）に差し替える。
- `migrations/` ディレクトリには変更を加えない。
- より広範なテーブル（`customer_score_history`、`alerts` 等）を含む包括的なパーティショニング戦略・移行ガイド・容量計画は WS-11 Task 9（`docs/decisions/0011-partitioning-strategy.md`、`docs/operations/partitioning-guide.md`）で扱う。本ADRはそれに先行する `audit_logs`/`transactions` 分の最小限のテンプレート提供についてのみ決定するものであり、WS-11 側の作業を妨げない。
