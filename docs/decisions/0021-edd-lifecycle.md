# [ADR-0021] EDD ライフサイクルの明示的な完了状態

| 項目 | 内容 |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-07 |
| 関連ADR | ADR-0016 |

## コンテキスト

EDD（強化された顧客管理）のウィンドウは、High tier のスコアで開始し、エスカレーションジョブで
段階を進むことはできたが、**終わらせる方法が存在しなかった**。

強化された顧客管理を実施した運用者は、それを記録する場所を持たなかった。顧客は未対応のまま残り、
エスカレーションの時計は回り続け、ウィンドウを終わらせるものは tier の降格だけだった。
そしてその降格は 4 つの段階タイムスタンプを nil にしていた——**通常の再スコアが、EDD が要求された
という事実とどこまでエスカレーションしたかの記録を破壊していた**。

読み取りモデルの `completion_status` は `not_required` / `open` / `escalated` の 3 値しか持たず、
完了した EDD も期限を大幅に超過した EDD も同じ `open` に見えた。`remaining_days` は 0 で
クランプされるため、200 日超過のウィンドウと当日期限のウィンドウが区別できなかった。

## 決定

**明示的な完了**: `POST /api/v1/customers/{id}/edd/{complete,reopen}` を新設する。
いずれも `rationale` を要求し、追記専用の `customer_edd_events` 行を actor とポリシー版とともに書く。

**降格時の証跡保持**: `edd_policy_v1` の `tier_downgrade: retain_evidence` を既定とし、
tier 降格ではウィンドウを `edd_closed_at` + `edd_close_reason = "tier_downgrade"` で閉じるが、
履歴は消さない。

**状態の拡張**: `completion_status` に `overdue` と `completed` を加える。

**`overdue_days` の新設**: 常に 0 以上で、期限超過の日数を数える。`remaining_days` は
1 リリース据え置き、スキーマ上 deprecated と記す。

**スケジュールの単一出典**: 30/60/90 は `edd_policy_v1` から取る。調査画面、エスカレーション
ジョブ、プロセス設定の 3 箇所のリテラルを廃する。既存の環境変数 2 本は互換のため残し、
ポリシーがあればポリシーが勝つ。

**ケースの記録**: エスカレーションジョブが開いたケースを `customers.edd_case_id` に記録する。
従来はケース要約の中のマーカー文字列との突合でしか辿れなかった。

## 根拠

「EDD が完了したか」は監査で必ず問われる。それに答えられないシステムは、EDD を実施していても
実施したことを示せない。閉じたウィンドウの履歴だけが、顧客の tier が動いた後になって
「強化された顧客管理は完了していたのか、誰が、どのような根拠で」に答えられる。

降格時に消していたのは、おそらく「EDD が不要になったのだから記録も不要」という判断だった。
これは逆である。要求されたが完了しなかった EDD の記録は、リスクが下がった後こそ重要になる。

`overdue_days` を加算的に足したのは、`remaining_days` を再定義すると既存クライアントが
黙って誤るからである。名前が意味と一致しないフィールドは、置き換えるのではなく、
正しい名前の隣に置いて deprecate する。

## 棄却した代替案

**`remaining_days` を負の値も返すように変更する。** 加算的でなく、0 でクランプされることを
前提にしたクライアントが黙って壊れる。

**完了をケースのクローズで表現する。** EDD ウィンドウとケースは 1 対 1 ではない。
ウィンドウが独自の終端状態を持つべきである。

## 影響

EDD ウィンドウが開いたまま無期限に残らなくなる。tier 降格が証跡を破壊しなくなる。

`completion_status` に新しい値が現れるため、この文字列で分岐しているクライアントは
`overdue` と `completed` を扱う必要がある。いずれも従来 `open` または `escalated` として
現れていた状態の細分化であり、既定の分岐に落ちる実装なら安全である。
