# [ADR-0025] 設定変更の検証段階とアラート来歴の解決

| 項目 | 内容 |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-08 |
| 関連ADR | ADR-0012, ADR-0014, ADR-0020, ADR-0024 |

## コンテキスト

DR-18（設定・ルール編集と activation の maker-checker、validation policy）は
Wave 4 の P29（#82）を、DR-19（アラート来歴の保持、参照解決、制限アクセス）は
P31（#84）を止めていた。

いずれも**既に決着している統制を、どこまで広げるか**という問いである。

- **ADR-0014** は activation に作成者 ≠ 承認者の 2 名を強制済みで、
  HTTP 経由で作られる新規ルールと新規バージョンは常に非活性である。
  ルールバージョンは immutable
- **ADR-0020** は「追記専用と保持は対立する義務ではなく粒度の問題」として、
  purge 対応の追記専用トリガを導入済み
- **ADR-0012** は運用者がエンジンへ直接与えるファイルの信頼境界を定めている

#82 が追加で求めるのは、編集の出発点を明示的な baseline にすること、
4 種のエラーを区別すること、活性化前に diff を見せることである。
#84 が求めるのは、認可されたレビュアーが識別子から検知時の実物を解決できること、
そしてレガシーアラートを `not_captured` とし現設定を backfill しないことである。

## 決定

### DR-18 — maker-checker は activation のみ、validation は四層

**ADR-0014 の範囲を広げない。**

- **下書きの保存に承認を要求しない。**非活性のバージョンは何の検知も変えないため、
  第二の署名が守るものがない
- maker-checker は **activation のみ**に課す（現行どおり）

**validation は 4 分類を区別して返す。**単一の「不正です」では、
運用者が直せるものと直せないものの区別がつかない。

| 分類 | 内容 | 位置情報 |
|---|---|---|
| `syntax` | JSON / YAML として読めない | line / column |
| `schema` | 読めるが必須項目や型が違う | JSON path |
| `cross_reference` | 単体では正しいが他の設定と矛盾する（存在しない scenario ID の参照など） | JSON path |
| `activation` | 定義は正しいが今この状態では活性化できない（ADR-0014 の二者統制不足など） | 位置なし |

**warning は activation をブロックしない。error のみブロックする。**
編集の出発点は「現在活性なバージョン」または「明示的に選んだサンプル」とし、
空欄から書き始めさせない。無変更の投稿は明示的にそう返し、成功に見せない。

### DR-19 — 来歴は digest 参照、実物は既存の rule_definitions

**新しい artifact store を作らない。**

- アラート生成時に rule/scenario ID、rule version、config digest、
  engine/evaluation version、評価窓、public-safe パラメータを
  **immutable に保存する**（migration `057`）
- **実物は既存の `rule_definitions` の immutable なバージョン行**を指す。
  ルールバージョンは ADR-0014 により既に不変である
- アラートの保持期間中、参照先のバージョン行を purge しない制約を
  ADR-0020 と同じ形（`retention.CustomerReferencingTables` に相当する
  機械検証）で強制する
- **参照先が解決できない場合は `missing` を返す。**推測も再構成もしない
- レガシーアラートは `not_captured`。**現在の設定を過去の事実として
  backfill しない**
- 制限された artifact の本文は API/UI へ返さず、opaque identifier と
  availability だけを返す（master plan PROV-01）
- バッチ・リアルタイム・リカバリの 3 経路すべてが同一の来歴セマンティクスを持つ

**pinned artifact による再処理は、現在設定での評価と区別できる形で記録する。**

## 根拠

DR-18 で下書きに承認を課さないのは、**統制は結果に対して課すもの**だからである。
非活性のバージョンは誰の判断も変えない。そこに第二の署名を求めると、
候補を試して backtest で比べる作業（#71）が毎回承認待ちになり、
統制が守るものより邪魔するものの方が大きくなる。

warning でブロックしないのも同じ理由である。警告が常態化した瞬間、
override は儀式になり、本当に危険な警告と区別できなくなる。

DR-19 で専用ストアを作らないのは、**ルールバージョンが既に immutable だから**である。
同じ内容を別テーブルへ複製すれば、全文重複のストレージコストに加えて、
PII や機密を含みうる blob の認可と purge という新しい問題を持ち込む。
ADR-0020 が示したとおり、これは保持の粒度の問題であって、保存場所の問題ではない。

`missing` を返して推測しないのは、Auditability First の直接の帰結である。
「検知時に使われた設定」を今の設定で埋めるのは、記録ではなく捏造になる。

## 棄却した代替案

**下書きの保存にも承認を要求する**: 統制は最も厳しいが、
試行錯誤のルール作成が毎回第二承認待ちになり、backtest で候補を試す
ワークフロー（#71）と衝突する。守っているのは活性化であって編集ではない。

**warning も activation をブロックする（明示的 override 付き）**: Fail-Alert に
最も忠実だが、警告が常態化して override が無意味になるリスクがある。
error と warning を分けた意味が失われる。

**専用の content-addressed artifact store**: `rule_definitions` の保持期間から
完全に切り離せるが、全文重複のコストと、blob の認可・purge 設計が新たに要る。
immutable なバージョン行が既にあるものを二重に持つ理由がない。

**識別子だけ保存し解決は提供しない**: 最小工数だが、#84 の
「認可されたレビュアーが実物を解決できる」を満たさない。
識別子だけの来歴は、照会できない限り主張にすぎない。

## 影響

- P29（#82）は ADR-0014 を変更せずに着手できる。追加されるのは
  validation の分類とその位置情報、および事前 diff の表示
- P31（#84）は migration **`057`** を使う（`056` は Wave 3 が消費済み）
- **アラートの保持期間が、参照先ルールバージョンの保持期間の下限になる。**
  保持期間内のアラートが参照するバージョン行は purge できない。
  この制約は機械検証で守り、migration で外部キーを足して
  ルールの purge を無期限に阻む形は取らない（ADR-0020 と同じ判断）
- 既存アラートは全件 `not_captured` として表示される。
  これは欠陥ではなく、来歴を記録していなかった事実の正確な表示である
- ルール定義ファイルを直接エンジンへ与える運用（ADR-0012）は本 ADR の
  統制下に入らない。その経路の来歴は config digest として記録されるが、
  実物の解決は運用者側の責務である
