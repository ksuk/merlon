# [ADR-0016] 単独メンテナ体制の変更統制とリリース

| 項目 | 内容 |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-16 |
| 関連ADR | ADR-0012, ADR-0014 |

## コンテキスト

本リポジトリの実働メンテナは1名である。この制約と、宣言済みの統制が噛み合っていなかった。

- [リポジトリガバナンス](../development/repository-governance.md)は「作成者は自分の変更を承認できない」と宣言し、`MAINTAINERS.md` は DB マイグレーションと監査ロール変更に第2の Admin レビューを要求していた。いずれも1名では成立しない。
- `main` の Ruleset は `required_approving_review_count: 0` で運用している。承認必須を有効化すると、第2のメンテナを追加する PR を含め、すべての PR がマージ不能になる。
- [リリースチェックリスト](../development/release-checklist.md)は本番リリースの事前条件にバックアップメンテナと独立したリリース承認者を置いていた。したがって本番リリースは事実上永久にブロックされていた。
- その結果、PR 単位のアドホックな逸脱記録（Issue #113）が発生した。恒常的な体制上の制約を PR 単位の例外として処理し続ければ、例外が常態化して記録自体の意味が失われる。

**メンテナが1名である限り、独立した承認は定義上成立しない。** これは実装の遅れではなく、体制から導かれる帰結である。

## 決定

**方針の各条項は、次のどちらかでなければならない。**

- **(a) 仕組みで強制されている**
- **(b) 事実の開示であり、ルールを主張していない**

「宣言されたが強制されないルール」というカテゴリを本リポジトリから排除する。宣言と実装のギャップは、遵守の意図があっても統制としては機能せず、監査においては「守られていない規程」として最も高くつく。

以下、この規準に照らして体制を定義する。

### 1. 単独メンテナで完結する（仕組みとしても方針としても）

1人で PR をマージし、1人でリリースを発行する。これを例外や暫定措置としてではなく、現時点の運用モデルとして定義する。将来、作成と承認を分離する進化パスは §5 に残す。

### 2. リリースは単一チャネル `vX.Y.Z`

プレリリースチャネル（`vX.Y.Z-rc.N`）は廃止する。かつてこのチャネルは「ガバナンス統制が未整備であること」を表す代理表現として機能していたが、統制の実態を**タグ名のサフィックスで伝えるのは弱い**。読み飛ばされるし、意味は文書を読まなければ分からない。

`.github/workflows/release.yml` の SemVer 正規表現はプレリリース識別子を**拒否する**。`scripts/changelog.mjs` はどのタグに対しても自分自身の `## [X.Y.Z]` 節を要求し、`[Unreleased]` へのフォールバックを持たない。仕組みが単一チャネルを強制する。

廃止時点でリリース実績はゼロ（`v*` タグなし、GitHub Release なし、GHCR パッケージなし）であり、移行対象の利用者は存在しない。

### 3. 統制の実態を成果物に開示する

タグ名から失われた情報を、より強い形で成果物側に載せる。**これが (b) の「事実の開示」の中核である。**

| 出力 | 内容 |
|---|---|
| `release-manifest.json` | `schema_version: 2`、`governance: {mode, independent_approval, separation_of_duties, adr}` |
| コンテナイメージ LABEL | `io.github.ksuk.merlon.governance.*`（同じ4項目） |
| GitHub Release 本文 | 冒頭に固定の開示ヘッダ。`CI Required` と `Security Required` がリリースコミット上で通過したこと（公開前にリリースワークフローが検証する）、ADR-0016 以降の PR がセルフレビュー証跡を持つこと（マージ時に強制。リリース側では再検証しない）、独立した承認と職務分離を**含まない**こと |

値は事実の記述にとどめ、弁明や評価を書かない。運用者は `docker inspect` またはリリースマニフェストの取得だけで、このソフトウェアがどのような統制の下で作られたかを機械的に判定できる。

`vX.Y.Z` が主張することは本プロジェクトの文書が定義する。定義したうえで成果物に刻む限り、1名体制で `vX.Y.Z` を発行することは虚偽の主張にはならない。虚偽になるのは、独立承認を主張しながら発行する場合である。

### 4. マージ統制はセルフレビュー証跡の必須チェック

承認の代わりに、作成者が「何をしたか」と「何を確認していないか」を記録に残す。これを運用上の約束ではなく**ゲート**にする。

- `.github/workflows/governance.yml` が `Governance Required` コミットステータスを head SHA に対して投稿する
- `scripts/check-self-review.mjs` が、`.github/SELF_REVIEW_TEMPLATE.md` 形式のコメントの存在、**投稿者が PR 作成者本人であること**、head SHA との一致、5つの必須セクションが**すべて非空**であることを検証する
- 証跡は head SHA と作成者の両方に束縛される。新しい push は証跡を無効化する（`dismiss_stale_reviews_on_push` と同じ意味論を、破棄すべきレビューが存在しないリポジトリで再現する）。作成者への束縛が必要なのは、本リポジトリが public であり head SHA も公開情報であるためである。形式のみを検査するゲートは通りすがりの第三者が充足でき、それは統制ではない
- 証跡コメントの削除も再判定の契機とする（`issue_comment` の `deleted` を購読する）。判定は一度投稿されると残り続けるコミットステータスであるため、削除を購読しなければ green が根拠より長く生き残る
- ワークフローのトリガーは `pull_request_target` とする。base コンテキストで実行されるため fork と Dependabot の PR にもステータスを書き込め、判定に使う検査スクリプトは常に `main` 側の写しになる。head 由来のコードは実行しない（checkout に `ref:` を与えず、コメント本文は標準入力で渡す）
- bot が作成した PR は自動的に success とする。bot はセルフレビューを書けず、満たしようのない必須チェックは依存更新 PR を恒久的に停止させる

「確認していない事項」セクションを非空必須にしているのは、そこが本来第2のレビュアーが担う情報だからである。空欄の証跡は証跡ではない。

リスク階層別のクールオフ時間は**採用しない**。強制する仕組みを持たない時間規則は (a) にも (b) にも当てはまらず、本 ADR の規準に反する。

### 5. 統制の自己参照問題と、その限界

すべての機械ゲートは、変更を作成するのと同一の Admin が管理している。作成者自身が変更できるチェックは代替統制であり、職務分離ではない。この事実は消せないため、変更を検知可能にする。

- `main` とリリースタグの Ruleset を `.github/rulesets/` にコミットし、弱体化がレビュー可能な差分として現れるようにする
- `.github/workflows/ruleset-drift.yml` が週次で実 Ruleset をエクスポートし、ベースラインとの差分で失敗する。エクスポートは既存ファイルへの上書きではなく、ベースラインを空にしてから書き出す。上書きでは、実設定から Ruleset が削除された場合にファイルが無変更のまま残り、差分が生じないためである。保護の撤去という最も強い弱体化が唯一の検出不能事象になるのは、ドリフト検知として成立しない
- `bypass_actors` は空、`current_user_can_bypass` は `never` を維持する

**この仕組みが検出できないもの。** 同一 Admin が実設定とベースラインを同じ操作で変更すれば差分は生じない。これは設計上の限界であり、緩和ではなく明示によって扱う。ドリフト検知が買うのは「気づかれずに弱体化しないこと」と「記録が残らずに弱体化しないこと」であって、意図的な同時改変を止めることではない。本リポジトリは個人アカウント配下にあり、リポジトリ層より上位の Organization/Enterprise 層の Ruleset は存在しない。

**ロックアウトからの復旧。** `bypass_actors` が空で `current_user_can_bypass` が `never` であるため、必須チェックが恒久的に報告不能になった場合、オーナー自身も `main` にマージできない。復旧手順は、Ruleset の `enforcement` を一時的に `evaluate` へ変更し、原因を修正してから `active` へ戻すことである。この一時変更はベースラインへのコミットとして記録する。記録のない `enforcement` 変更はドリフトとして扱う。

### 6. 将来: 作成と承認の分離

第2 Admin が着任した時点で、次に移行する。

1. `MAINTAINERS.md` と `.github/CODEOWNERS` に記載し、オンボーディングを完了する
2. `scripts/configure-github-ruleset.sh --apply --require-approvals` を適用する（`required_approving_review_count: 1`、`require_code_owner_review`、`require_last_push_approval`）
3. `.github/rulesets/` のベースラインを更新する
4. リリース成果物のガバナンス開示（`mode`、`independent_approval`）を実態に合わせて更新する
5. 単独メンテナ期にマージされた変更を、オンボーディングの一環としてレビューする（`MAINTAINERS.md` の Backup Onboarding に既に含まれる）

「着任」とは、リポジトリの Admin 権限を保持し、上記1を満たした状態を指す。権限の付与だけでは着任としない。

本体制の**見直し期限は 2027-02-16** とする。これは事実の開示であって、期限到来時に自動的に何かが停止するという主張ではない。1人運用は時限的な逸脱ではなく現時点の意図した運用モデルであり、失効演出を伴う期限は (a) にも (b) にも当てはまらない。

### 7. 本 ADR 自体のブートストラップ問題

本 ADR を導入する変更は、本 ADR が定める `Governance Required` の対象である。しかしその仕組みは、この変更がマージされるまで存在しない。したがって**この決定自体は、自らが定める統制の下で承認されたものではない**。自己承認である。

これは手続きで解消できない。統制を新設する最初の変更は、常にその統制の外側にある。できるのは3点だけである。

1. 事実として記録する。本 ADR の導入は単独メンテナによる自己承認のブートストラップであり、事前の誤りを防ぐ統制は働いていない。
2. 第2 Admin 着任時のレビュー対象の筆頭に置く。統制設計そのものの誤りは、その統制下でマージされた個別の変更の誤りより影響が大きい。
3. 導入前より弱くならないことを確認する。導入前の状態は「宣言された統制が守られず、PR 単位のアドホックな例外で処理される」であり、セルフマージは既に行われていた。本 ADR はセルフマージを新たに許可するのではなく、既に行われているセルフマージに検証可能な証跡を課す。

3 は本 ADR の妥当性の根拠ではなく、ブートストラップを許容する根拠にすぎない。統制設計の妥当性そのものは、遡及的なレビューでしか検証できない。

## 根拠

宣言した統制を守れない状態を続けるより、守れる統制を宣言して仕組みで守る方が、監査可能性は高い。これはリポジトリガバナンスが既に採っている立場（宣言しながら実装していない統制は、明示されたギャップより悪い）の延長であり、今回それを規準として明文化した。

プレリリースチャネルの廃止は、統制を緩める方向に見えて逆である。rc という迂回路は「本番相当の統制がないこと」を暗黙に伝える仕組みだったが、暗黙である以上は伝わらないことがある。同じ情報を `release-manifest.json` と OCI ラベルに機械可読で出せば、運用者のベンダー審査は文書を読まなくても答えを取得できる。AML/CFT の記録を生成するシステムを導入する規制対象事業者にとって、この差は小さくない。

クールオフを実装せず削除したのは、実装コスト（`issue_comment` トリガーで head SHA に対してチェックを再報告する仕組みに、さらに時刻計算を重ねる）に対して、1人運用で24時間待機が実際に守られる保証がないためである。守られない規則を持つより、証跡の存在と内容を確実に検証する方が統制として強い。

## 棄却した代替案

**2つ目の GitHub アカウントを作成して承認する。** 棄却理由は2つあり、性質が異なるため分けて記す。第一に、独立性を偽装する目的での別アカウント運用は、プラットフォームが保持する記録（品質基準の証跡区分 E3）に「独立した承認」という虚偽の事実を作り出す。これは規約の解釈にかかわらず成立する棄却理由であり、正直なセルフマージより悪い。監査で最も発見されにくく、発見されたときに最も高くつく。第二に、GitHub の利用規約は1名が保持できる無料アカウントを1つに制限しており、無料アカウントの追加作成はこれに抵触する。第一の理由だけで棄却として十分である。

**必須ゲートを外してマージを容易にする。** 人的レビューが成立しない体制では、機械ゲートが唯一残る検出手段である。人が減った状況で機械の検出力を下げるのは方向が逆である。

**本番チャネルを凍結し、rc のみを提供し続ける。** 前案。統制を強めるように見えて、実際には「手続きはあるが未達」という説明を続けることになり、かつプレリリースという迂回路の維持コストを恒久的に負う。開示を成果物に載せる方が、正確でありコストも低い。

**AI によるレビューを独立レビューとして数える。** 自動レビューは有用な検出手段であり、代替統制として記録してよい。しかし責任を負う独立した人間ではないため、職務分離の充足として記録してはならない。

**リスク階層別のクールオフを宣言だけしておく。** 本 ADR の規準に真正面から反する。実装しないなら削除する。

## 影響

運用者への説明が変わる。「本番リリースは準備中」でも「rc のみ提供」でもなく、「`vX.Y.Z` を提供する。そのタグが何を主張し何を主張しないかは成果物に記載されている」となる。[コンテナイメージ](../operations/container-images.md)、README、[FAQ](../faq.md)、[サプライチェーン](../security/supply-chain.md)をこれに合わせる。

復元訓練と脆弱性対応訓練は**引き続き必須**とする。これらは1人で実施できる実質的な技術統制であり、不可能なのは「独立したオブザーバーによる承認」の一節だけである。当該署名要件を削除し、独立オブザーバーが存在しない旨を記録に明記する形に置き換える（`SECURITY.md`、[バックアップと復元](../operations/backup-restore.md)）。

Issue #113 は本 ADR に置換される。あれは「逸脱」の記録だったが、単独メンテナでの完結は逸脱ではなく文書化された運用モデルになったため、時限的な例外として維持する対象ではなくなる。
