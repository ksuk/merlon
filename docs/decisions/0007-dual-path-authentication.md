# [ADR-0007] 二経路認証（JWT セッション + APIキー M2M）

| 項目 | 内容 |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-07-04 |
| 関連ADR | なし |

## コンテキスト

Merlon には性質の異なる2種類のクライアントが存在する：人間のオペレータ（UI からログインし、ケース調査・アラート確認等の対話的操作を行う）と、非対話クライアント（基幹連携アダプタ、Webhook 送信元、CLI、バッチジョブ）。現行実装（merlon 公開リポジトリ）は APIキー認証のみを提供していたが、AUTH-001（ローカルユーザ認証）の追加にあたり、この2種類のクライアントを単一の認証方式で扱うか、用途別に使い分けるかを決定する必要があった（ローカルユーザ認証とAPIキー認証の要件）。

## 決定

人間のオペレータは JWT ベースのセッション認証、非対話クライアントは APIキー認証を用いる、二経路併存の方式を採用する。

**JWT セッション認証（SEC-004）：**
- アクセストークン（JWT, 有効期限15分）＋リフレッシュトークン（DB管理, 有効期限7日, ローテーション方式）の2トークン方式
- 署名は RS256（本番）を基本とし、鍵ペア未導入時の暫定として HS256（開発用、`MERLON_JWT_SECRET`）を許容する
- アクセストークンの即時失効のため、Redis 上に短命な失効リスト（Denylist）を設ける
- クライアント側はアクセストークンを `HttpOnly`+`Secure`+`SameSite=Strict` Cookie に保存する

**APIキー認証（AUTH-006）：**
- `Authorization: Bearer <key>` 形式。キー自体はランダム32バイト以上、DB には SHA-256 ハッシュのみ保存（平文不保持）
- APIキーにも RBAC ロールを紐付け、最小権限の原則に従う（取込み専用キーは analyst 相当に留める等）
- 管理者による即時失効が可能。発行・失効・最終使用日時は監査ログに記録する
- 初期セットアップ完了前に限り、環境変数のブートストラップトークンで最初の管理者を作成できる（セットアップ完了後は無効化）

両者は同一の RBAC ロール体系（Admin/Analyst/Viewer）に対して認可判定を行い、レート制限もユーザ単位/APIキー単位で同様に適用する。

## 根拠

- 人間のセッションと M2M 呼び出しは失効・ローテーション・保存場所の要件が根本的に異なる。JWT+リフレッシュトークンのローテーションは対話的セッションの「短命アクセストークン+安全な再認証」に適しているが、バッチジョブや基幹連携アダプタのような長時間稼働・自動化されたクライアントには不向き（15分ごとの再認証フローを組み込む必要が生じる）
- 単一方式（例：全クライアントを JWT に統一）にすると、非対話クライアントがリフレッシュトークンのローテーションを自前で実装する必要が生じ、実装が複雑化する。逆に全クライアントを APIキーに統一すると、ブラウザセッションでの XSS 耐性（HttpOnly Cookie）や強制失効の即時性（Denylist）といった、人間の対話的操作に必要なセキュリティ特性が得られない
- 現行実装が APIキー認証のみを提供していたため、後方互換性の観点からも APIキーを M2M 用途として存続させ、UI ログインのみ JWT セッションへ移行する方が既存導入への影響が小さい（Contract Stability）
- APIキーを SHA-256 ハッシュのみで保存するのは、DB 漏洩時にも平文キーを復元不可能にするため（パスワードの Argon2id ハッシュ化と同じ設計思想）

## 棄却した代替案

- **全クライアントを JWT セッションに統一** — 非対話クライアント（バッチジョブ、基幹連携アダプタ）がリフレッシュトークンのローテーションとセッション管理を自前実装する必要が生じ、M2M 用途としては過剰に複雑
- **全クライアントを APIキーに統一** — ブラウザセッションに必要な XSS 耐性（HttpOnly Cookie 保存）や、パスワード変更・ロール変更時の即時反映（Denylist）が得られず、対話的操作のセキュリティ要件を満たさない
- **OAuth2/OIDC 外部 IdP 連携を必須とする** — セルフホスト製品として追加の外部依存（IdP）を導入前提にすると、小規模導入での導入障壁が上がる
