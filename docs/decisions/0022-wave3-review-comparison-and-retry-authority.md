# [ADR-0022] スクリーニング判定・バックテスト比較・再評価再試行の権限境界

| 項目 | 内容 |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-08 |
| 関連ADR | ADR-0014, ADR-0016, ADR-0018, ADR-0020 |

## コンテキスト

Wave 3 の実行票は 9 件の Decision Required を挙げていた。うち DR-13〜16 は ADR-0016 が、
DR-11 は ADR-0018 が解決している。残る **DR-08（スクリーニング判定）、DR-10（バックテスト比較）、
DR-12（保留評価の再試行）** は実装の中で事実上決着していたが、どこにも記録がなかった。

3 つは別々の画面に見えて、同じ問いを共有している。**「システムが下した判定を、誰が、
どういう証跡と引き換えに覆せるか」**である。記録がないまま実装だけが存在する状態は、
次の担当者が「なぜこの権限なのか」を判断できず、Wave 4 で同じ問いを別の答えで実装する。

具体的な失敗の形はそれぞれ次のとおりだった。

- **DR-08**: 判定 enum も遷移規則もなく、`FALSE_POSITIVE` と判定した対象が再スクリーニングの
  たびに新しいヒットとして未処理キューへ戻っていた。運用者は同じ対象を何度も判定し直す。
  かといってヒットを捨てれば、制裁リスト側が更新されて本当に危険になった対象を見落とす
- **DR-10**: 比較のベースラインが「実行時にアクティブだったもの」で、あとから変わる。
  比較結果を再現できず、`affected_customer_ids` はフラットな ID 配列でしかないため
  「アラートが増えたのか減ったのか」を表現できなかった
- **DR-12**: 自動再試行に上限がなく、恒久的に失敗するレコードを永久に叩き続ける。
  一方で運用者による手動復活と自動再試行が同じカウンタを共有しており、
  人が何回押したかが監査証跡に残らなかった

## 決定

### DR-08 — スクリーニング判定は前進のみ、過去判定は抑制であって破棄ではない

**判定 enum と遷移**: `NEW → REVIEWING → {TRUE_POSITIVE, FALSE_POSITIVE}` のみ
（`domain/screening_result.go` の `screeningResultTransitions`）。
列挙にない遷移はすべて拒否する。**終局判定からの逆行（`FALSE_POSITIVE → TRUE_POSITIVE` を含む）は
禁止**とし、訂正は新しいスクリーニング実行が生む新しい結果行で表現する。
`FALSE_POSITIVE` へ移す際は理由テキストを必須とする。

**メーカー・チェッカーは判定そのものには課さない**。`TRUE_POSITIVE` は同一トランザクション内で
**critical 優先度のケースを 1 件だけ**生成し、以後の二重承認義務はケース側の disposition
（ADR-0014 系の dual control）へ委ねる。スクリーニング判定に独自の承認段を重ねると、
同じ事実に対して二つの承認台帳ができる。

**再スクリーニング時の旧判定**: 同一顧客 × 同一リストエントリに過去の `FALSE_POSITIVE` があれば、
新しいヒットを `suppressed = true` / `suppression_reason = "prior_false_positive:<過去の判定ID>"`
として**記録した上で**既定キューから外す（`screening/scheduler.go`）。
**抑制はヒットを隠すのであって、落とさない**。抑制されたヒットも永続化され、
`suppressed` フィルタで明示的に取得できる。

抑制のスコープは**顧客 1 件 × エントリ 1 件**に限定する。別の顧客の同一エントリへのヒット、
および同一顧客の別エントリへのヒットには波及しない。ある人物について「同姓同名の別人だった」
と判断したことは、別の人物についての判断ではない。

### DR-10 — ベースラインは実行時にピン留めし、差分は方向を持つ

**ベースラインの正本**: リクエストの `baseline_rule_set_id`。未指定時のみ `"active"` を既定とするが、
これは**起票時に解決してジョブ行へ焼き付ける**（`BaselineRuleVersion`、`BaselineRuleDefinition`、
`stableDigest` を `BacktestMetadata.BaselineSnapshot` へ保存）。以後アクティブなルールセットが
入れ替わっても、過去の比較結果の意味は変わらない。ベースラインと候補が同一なら 400 で拒否する。

**比較メトリクス**: シナリオ単位の `delta_kind`（`added` / `removed` / `unchanged`）を
`backtest_job_affected_customers` に 1 行ずつ持つ（migration 051）。フラットな ID 配列では
表現できなかった「候補ルールセットならこの顧客にアラートが出始める／出なくなる／変わらない」を
一次データとして持ち、読み出しは keyset 走査になる。

**履歴の保持**: `backtest_job_affected_customers` は `job_id` に `ON DELETE CASCADE` を張るが、
**`customer_id` には外部キーを張らない**。この行は過去のある時点でルールセットが何を計算したかの
証跡であり、保持期間を過ぎた顧客の purge を過去の比較が拒否してよい理由はない（ADR-0020 と同じ原則）。

### DR-12 — 自動予算と人間の判断を別のカウンタに分ける

**自動再試行の上限**: `maxPendingRetries = 5`（`batch/recovery.go`）。使い切ったレコードは
`FAILED` にした上で `"automatic retry limit reached"` を理由にエスカレートする。
永久に叩き続けない。

**バックオフ**: 個別レコードごとの指数バックオフは持たず、回収ジョブの
固定ポーリング間隔 `defaultPollInterval = 30s` と、1 回の実行あたり
`recoveryPageSize = 100 × maxRecoveryPagesPerRun = 10` という処理量上限で律速する。
キューの読み出しは「purge 対象外の PENDING_REVIEW を古い順」であり、
その順序ごと索引に持たせる（migration 052 の `idx_pending_evaluations_queue`）。

**手動復活の権限とカウンタ**: `manual_retry_count` を `retry_count` とは**別カラム**にする
（migration 052）。運用者の復活は「原因は直った、もう一度やれ」という自動再試行とは
異なる主張であり、同じカラムで数えると手動操作が自動予算を消費・リセットし、
かつ「人が何回押したか」が監査証跡から消える。

自動予算を使い切ったレコードの `manual_retry` は、**システム自身の結論を覆す操作**なので
ホワイトリスト登録の承認と同格の権限 `whitelist:approve` を要求する
（`server/wave3_batch.go`）。全アクションが `expected_version` を要求し、
`pending_evaluation_history` へ追記される。

**デッドレター**: `FAILED` は削除しない。保持期間処理の対象になるまでキューに残り、
フィルタで明示的に取り出せる。取りこぼしを静かに消すより、溜まっていることが見える方を選ぶ。

## 根拠

3 つの決定に共通する規準は **Fail-Alert** と **Auditability First** である。

抑制、上限、権限のいずれも「見落とさない」を優先して設計した。抑制はヒットを消さず隠すだけ、
再試行上限はレコードを消さずエスカレートするだけ、権限は操作を禁じるのではなく
より高い権限と証跡を要求するだけである。どれも**情報を減らす方向には働かない**。

判定の逆行を禁じてカウンタを分けたのは、監査証跡が「今の状態」ではなく
「誰がいつ何を主張したか」の連なりであるべきだからである。上書き可能な単一の値は、
それが上書きされた瞬間に証跡としての価値を失う。

## 棄却した代替案

**スクリーニング判定に独自のメーカー・チェッカーを課す**: 同一事実に対する承認台帳が
ケースと二重化する。承認者が両方で異なりうる状態は、監査時にどちらが正本か答えられない。

**再ヒットを完全に抑止する（記録しない）**: 制裁リスト側の更新で同一エントリの内容が
変わった場合に見落とす。抑制は表示の問題であって、記録の問題ではない。

**レコードごとの指数バックオフ**: 個別のスケジュール状態を持つと、回収ジョブが
ステートフルになり再起動耐性の検証面が増える。処理量上限で律速すれば、
恒久的な失敗は 5 回で終端するので、バックオフが解く問題自体が小さい。

**`retry_count` を手動復活時にリセットする**: 自動予算が実質無限になる。
「5 回で諦める」という上限が、人が押し直すたびに失効する。

**バックテスト履歴の `customer_id` に外部キーを張る**: 過去の比較証跡が
顧客の保持期間処理を無期限に阻む。ADR-0020 で同じ構図をすでに棄却している。

## 影響

- スクリーニングキューの既定表示は抑制済みヒットを含まない。運用者が過去の
  `FALSE_POSITIVE` 判定を見直したい場合、`suppressed` フィルタで明示的に取得する必要がある
- `TRUE_POSITIVE` は critical ケースを生む。ケース優先度の分布はスクリーニング判定の
  頻度に直接影響する
- バックテストのベースラインが起票時に固定されるため、「今のアクティブ設定と比べる」には
  ジョブを新規に起票する必要がある。過去ジョブの再解釈はできない
- 自動予算を使い切ったレコードの復活には Admin 相当の権限が要る。
  認証を構成していないデプロイでは `auth.RoleFromContext` が role を返さないため
  この検査は行われない（ADR-0018 と同じ扱い）
- `manual_retry_count` の追加により、保留評価の API レスポンスは additive に 1 フィールド増える
