# [ADR-0023] アラート・ケース・届出ライフサイクルの権限境界

| 項目 | 内容 |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-08 |
| 関連ADR | ADR-0014, ADR-0018, ADR-0019, ADR-0022 |

## コンテキスト

Wave 1 と Wave 2 の実行票は DR-01〜DR-07 を Decision Required として挙げていた。
実装はそのうち 5 件を事実上決着させたが、**どれも記録されていない**。

ADR-0022 が DR-08〜12 について解いたのと同じ問題である。実装だけが存在して根拠がない状態は、
Wave 4 で同じ問いに別の答えを出す。とくに DR-02（終局遷移の経路）と DR-03（届出後の訂正）は
状態機械そのものを決めており、後から変えると既存の監査証跡の意味が変わる。

残る DR-06（オーナーシップ階層）と DR-07（SLA ポリシー）は**実装されておらず、
決定もされていない**。この 2 件は本 ADR では解かず、Wave 4 の前提として明示する。

## 決定

### DR-01 — 取引一覧は顧客スコープ必須

`GET /api/v1/transactions` は `customer_id` を必須とする（`server/transaction.go`）。
グローバル一覧は提供しない。取引は最も件数が多く最も機微なリソースであり、
スコープなしの既定一覧は「全顧客の取引を返す」を既定動作にしてしまう。
UI は先に顧客セレクタを提示する。

### DR-02 — 終局クローズは `investigating` / `escalated` を経由する

`open` から `closed_true_positive` / `closed_false_positive` への直接遷移を**禁止**する
（`domain/alert.go` の遷移表、`domain/alert_test.go` が固定）。
`open → investigating` または `open → escalated` を経てからでなければ終局できない。

未着手のアラートを一度も調査せずに終局させられる経路は、「誰も見ていないが閉じている」
という状態を作る。1 クリックの誤操作が調査記録ゼロの終局を生む経路は塞ぐ。

終局遷移には rationale と confirm を必須とする（`server/alert.go`）。
`suppressed` はシステム／ホワイトリスト専用で、operator の PATCH からは到達できない。

### DR-03 — 訂正は新しい版であって、過去の書き換えではない

**STR**: `corrects_report_id` と `supersedes_report_id` を持つ**新しいレポート**として表現する
（`domain/report.go`）。提出済みレポートを draft へ戻す経路も削除する経路も設けない。

**ケース**: `closed → reopened` は許すが、`str_filed` は**出口のない終局状態**とする
（`domain/case.go`「str_filed has no outgoing edges」）。届出済みケースの訂正は
新しい STR 版と、必要なら新しいケースで表現する。

過去の disposition を書き換え可能にすると、監査証跡が「いつ何が主張されたか」の記録ではなく
「今どう見えるか」の記録に退化する。

### DR-04 — STR 提出に第二承認者は課さない

`POST /api/v1/reports/str/{id}/submit` は `submission_evidence` を必須とするが、
**提出者と別人の承認は要求しない**（`server/report.go`）。

#62 の受入基準が求めるのは「明示的で検証された遷移」と「提出証跡」であり、
メーカー・チェッカーではない。届出の期限性を考えると、第二承認者の不在が提出を止める設計は
規制上の締切に対して安全側ではない。提出は 1 人で行え、
事後の訂正は DR-03 の版管理で追える、という組み合わせを選ぶ。

同一 idempotency key の再送は同一結果を返し、silent overwrite は起きない。

**この決定は一括実行（ADR-0018）や CDD スコア上書き（ADR-0019）が dual control を課すのと
非対称である**。両者は「取り返しのつかない副作用を伴う内部操作」であり、
STR 提出は「期限のある外部報告」なので、優先する failure mode が違う。

### DR-05 — 届出証跡はケース側の終局遷移で強制する

ケースを `str_filed` にする際、`filing_channel`・`destination`・`external_reference` の
3 つすべてを必須とする（`server/investigation.go`）。加えて、
**提出済み** STR レポートの ID が必要で、そのレポートの source alert が
当該ケースにリンクされていることをサーバが検証する。

チャネル別に必須項目を変える policy 文書は**作らない**。届出先ごとの必須項目は
接続先が決まって初めて確定する。3 項目を無条件に必須とする方が、
空の policy を「要件なし」と読める状態より安全側である。

### DR-06 / DR-07 — 本 ADR では解かない

**オーナーシップ階層（DR-06）と SLA ポリシー（DR-07）は未決定であり、未実装である。**

現状あるのは次だけである。

- `assigned_to` / `assigned_team` / `due_at`（`domain/alert.go`、`domain/case.go`）
- `mine` / `unassigned` / `team` / `overdue` / `min_age_days` / `max_age_days` の
  サーバ側キューフィルタ（`server/queue.go`）

`due_at` は**クライアントが PATCH で設定する値**であり、ポリシーからサーバが計算していない。
したがって master plan §2.5 の `SLARef`——`policy_id`、`policy_version`、`basis_at`、
`state: not_configured|running|paused|breached|met`、`evaluated_at`——は存在しない。

これは #66 の受入基準の欠落ではない（#66 が求める due/SLA state のフィルタと表示は
`due_at` + `overdue` で満たされている）。欠けているのは master plan が SLA-01 として
掲げた**ポリシー駆動の SLA 契約**の方である。

**Wave 4 の P27（#79）着手前に DR-06 と DR-07 を解決すること。**
#79 は「SLA ポリシー未設定を明示的に示し、0 件や healthy として扱わない」を要求しており、
ポリシーという概念が存在しない現状ではその区別を表現できない。

## 根拠

DR-01〜DR-05 に共通する規準は **Auditability First** と **Fail-Alert** である。

スコープ必須、終局前の調査経由、版による訂正、証跡 3 項目の必須化は、いずれも
「記録が残らない経路」を塞ぐ方向に働く。DR-04 だけは逆に見えるが、
ここで守っているのは「期限内に届け出られること」であり、優先する失敗が違うだけである。

DR-06/07 を先送りするのは、SLA が**運用ポリシーの表現**であって
実装の詳細ではないからである。営業日カレンダー、一時停止条件、優先度マトリクスは
導入組織ごとに違い、既定値を勝手に決めると「設定した覚えのない SLA で期限超過と表示される」
という、未設定を healthy と表示するのと同じくらい悪い状態を作る。

## 棄却した代替案

**取引のグローバル一覧を提供し、既定で件数制限をかける**: 制限は表示の都合であって
認可ではない。既定で全顧客横断のデータを返す設計そのものを避ける。

**`open` からの直接終局を許し、rationale 必須で担保する**: rationale は
「調査した」ことの証明にならない。経路自体を塞ぐ方が検証可能である。

**提出済み STR の編集を許し、版を自動採番する**: 「編集した」と「訂正版を出した」は
規制上まったく別の主張である。API の形が同じなら、運用者は区別しない。

**STR 提出にも dual control を課す**: 承認者が不在の時間帯に届出が止まる。
期限のある外部報告で、内部統制のために締切を落とす取引は選ばない。

**チャネル別必須項目の policy を今作る**: 接続先が未定のまま作った policy は
空になり、空の policy は「要件なし」として通る。無条件 3 項目必須の方が強い。

**SLA の既定ポリシーを置く（例: 重大度別 24/72 時間）**: 設定した覚えのない期限で
期限超過が表示される。SLA-01 が禁じている「未設定を healthy と扱う」の裏返しの誤りである。

## 影響

- 取引画面は顧客選択なしにデータを表示しない。一覧からの横断調査は
  `GET /customers/{id}/investigation`（#76）が担う
- `open` のアラートを終局させるには 2 回の遷移が要る。一括クローズも同じ規則に従う
- `str_filed` ケースは再オープンできない。運用上の訂正は新しいケースを起こす
- STR 提出は 1 人で完結する。組織が第二承認を求める場合、
  現状は運用手順で担保するしかない（システムは強制しない）
- **Wave 4 P27 は SLA ポリシー契約を自ら定義する必要がある**。
  DR-06/DR-07 の解決が P27 の着手条件になる
