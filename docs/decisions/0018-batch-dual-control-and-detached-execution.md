# [ADR-0018] 一括実行のデュアルコントロールとリクエスト非依存の実行

| 項目 | 内容 |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-07 |
| 関連ADR | ADR-0014, ADR-0016, ADR-0022 |

## コンテキスト

このADRはDR-11（一括実行のスコープ上限、全件実行権限、大規模実行の二重承認、preview有効期限）を解決する。

対象マニフェストの preview → confirm 機構は、大量実行の前に「誰に対して何をするのか」を
凍結して見せるために存在する。その機構に 3 つの穴があった。

1. **サイレント切り捨て**。フィルタ解決が顧客を 10,001 件だけ読んでからフィルタしていた。
   5 万件の書籍で 200 件がマッチするフィルタは、「最初の 10,001 件の中でマッチした分」だけの
   マニフェストを**エラーも警告もなく**生成した。`target_count` は運用者が「これで全部」と
   読むのが自然な値である。
2. **無認可の実行**。confirm ルートは粗い role チェックを素通りし、マニフェストが何件を
   対象にしているかはルートミドルウェアからは見えない。
3. **rerun による迂回**。`handleRerunBatchRun` がマニフェストを `Status:"confirmed"` 決め打ちで
   clone して即実行していた。任意の規模の母集団を、過去のある時点で解決された内容のまま、
   第二の確認も第二の人間もなしに再実行できた。

加えて、実行が `r.Context()` の上で回っていた。クライアント切断（閉じたノート PC、1 万件の
バッチに対するプロキシのタイムアウト）で実行と確定の両方がキャンセルされ、`status=running` と
消費済みマニフェストがプロセス再起動まで固着した。

## 決定

**完全な解決**: 顧客を 1,000 件ずつ keyset で走査し、書籍全体にフィルタを適用する。
マッチが 10,000 を超えれば従来どおり 400。走査が 200,000 行を超えたら
「母集団が大きすぎる。フィルタを絞れ」の明示的な 400 を返す。部分的なマニフェストは決して返さない。

**デュアルコントロール**: 1,000 件を超えるマニフェストの confirm には、新設の
`batch:execute:large` 権限（Admin のみ）と、preview した本人以外の操作者を要求する。
判定はハンドラ内で行う（ルートミドルウェアはマニフェストを読めない）。

権限判定は**デプロイの設定**（`s.apikeys`、authMiddleware が使うのと同じ条件）を見る。
リクエストに role がないことから判断しない。認証を構成していないデプロイでは role 検査を
行わず、職務分離の検査は行う。

**リクエスト非依存の実行**: 起票トランザクションの commit 後に **202 Accepted** で run を返し、
実行は `context.WithoutCancel(r.Context())` に切り離した goroutine で継続する。

**キャンセル**: `POST /api/v1/batch/runs/{id}/cancel` を新設。実行ループが顧客の**あいだ**で
永続ステータスを確認する。既に処理した分は保持し、`cancelled` は `failed` / `partial` とは
別の終端状態とする。

**rerun（互換性破壊①）**: clone を `Status:"preview"` で作り、token とともに返す。
明示的な confirm を経なければ実行できない。

## 根拠

201 → 202 は正直な記述である。run は起票されたが完了していない。両方 2xx で、UI クライアントの
`request()` はコードで分岐しないため実害はないが、契約変更として CHANGELOG に記載する。

キャンセルを顧客の境界でのみ確認するのは、評価を開始した顧客は必ず完了・永続化させるためである。
中途半端に書かれた結果を残さない。

`cancelled` を独立の終端状態にしたのは、**何も失敗していない**からである。人が止めた。
失敗として記録すれば、後日の運用レビューでエンジン障害と区別できなくなる。

権限判定をデプロイ設定から取るのは、リクエストごとの role の有無から判断すると、
authMiddleware を通らない経路が生まれたときにこのゲートも同時に迂回されるからである。
ゲートは仮定する側であってはならない。

rerun の破壊を受け入れたのは、加算的な代替がないためである。「確認を経ずに実行できる」ことを
取り下げるのが目的であり、取り下げは定義上破壊的である。

## 棄却した代替案

**rerun を廃止する。** 再実行は正当な運用行為である。禁止ではなく、初回と同じ統制を通す。

**大規模実行を全面禁止する。** 年次の一括再スコアは必要な業務である。禁止ではなく承認を要求する。

**キャンセル時に処理済み分をロールバックする。** 誤った規模で走ったバッチのスコアが誤りとは
限らない。取り消すべきなら、その判断は別の操作として明示的に行うべきである。

## 影響

**互換性破壊①**: `POST /batch/runs/{id}/rerun` のレスポンスが、起動済みの run ではなく
確認待ちのマニフェストになる。呼び出し側は返された token で confirm を行ってから
`POST /batch/runs` する必要がある。

`POST /batch/runs` は 201 ではなく 202 を返す。結果は `GET /batch/runs/{id}` でポーリングする。

1,000 件を超えるバッチは、認証を構成したデプロイでは 2 人を要する。
