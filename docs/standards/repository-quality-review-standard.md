## 第I部 総則 — 共通評価モデル

### 1. 目的と適用範囲

#### 1.1 目的

本標準の目的は、次の 3 点を保証することにある。

1. **一貫性** — 異なる監査人(人間・AI エージェントを問わず)が同一リポジトリを評価したとき、同等の観点・尺度・判定手続に基づく評価結果が得られること。
2. **再現性** — 評価結果のすべての所見が、リポジトリ内の具体的なエビデンス(ファイルパス・行番号・コミット ID・実行記録)まで遡って検証できること。
3. **比較可能性** — 同一リポジトリの経年比較、および同一プロファイル(4.2 節)内でのポートフォリオ横断比較が意味を持つこと。

#### 1.2 適用範囲

- **評価対象**: Git リポジトリ全体。作業ツリー(最新リビジョンのファイル群)だけでなく、VCS 履歴、リポジトリ内に保持される CI/CD 定義、および取得可能な場合はホスティングプラットフォームのメタデータ(Pull Request、レビュー記録、Issue、リリース)を含む。
- **適用可能な形態**: OSS プロジェクト、社内プロダクト、受託開発成果物、規制産業システム。単一リポジトリ・モノレポの双方(モノレポの扱いは 7.5 節・8 章)。
- **技術スタック**: 非依存。本書の確認方法・判断基準は、特定言語・ビルドツール・ホスティングサービスの機能を前提とせず、それらは例示としてのみ言及する。

#### 1.3 非目標

本標準は次の目的には**使用しない**。

- 個人の人事評価・パフォーマンス測定(コミット数・作者別統計を個人評価に転用することを明示的に禁止する)
- 稼働中システムに対する侵入テスト・実地脆弱性診断の代替
- 事業性・プロダクト戦略・ロードマップの妥当性評価
- 法令・規制への適合の保証(本標準は適合性評価の**材料**を提供するが、法令解釈の最終判断は行わない。D12 参照)

#### 1.4 チェックリストではなく評価フレームワークである理由

チェックリストは「特定時点・特定対象・特定目的」に最適化された導出物であり、それ自体を標準化すると次の劣化が起きる: 項目の形骸化(Yes/No の形式充足)、文脈の無視(OSS ライブラリに運用 Runbook を要求する類)、尺度の欠如(重大な欠陥と軽微な改善が同じ 1 項目として数えられる)。

本標準はこれを避けるため、次の 4 層を定義する。

| 層 | 内容 | 本書での定義箇所 |
|---|---|---|
| 意味論 | 各領域で何を・なぜ評価するか | 第II部 各領域の「評価目的」「評価項目」 |
| 尺度 | 成熟度(L0〜L4)と重大度(Blocker〜Info) | 2 章・3 章 |
| 手続 | エビデンス収集・判定・集約・報告の手順 | 4〜7 章 |
| 適応 | 対象の性質に応じた調整規則 | 8 章(テーラリング) |

監査ごとのチェックリストは、この 4 層から「対象プロファイル + テーラリング記録」を入力として**生成**する。生成されたチェックリストの各項目は、必ず本書の評価項目 ID(例: D6-1)に遡れなければならない。

### 2. 成熟度スケール(L0〜L4)

すべての評価項目は、次の 5 段階の成熟度スケールで判定する。段階の定義は CMMI の成熟度概念に着想を得ているが、リポジトリ単位の評価に合わせて再定義したものである。

| レベル | 名称 | 判定アンカー |
|---|---|---|
| **L0** | 不在 | プラクティスが存在しない。または痕跡(空のテンプレート、放置された設定)のみで機能していない |
| **L1** | 場当たり | プラクティスは存在するが、個人依存で一貫性がない。文書化されておらず、実施の有無が担当者次第 |
| **L2** | 反復可能 | チームの慣行として一貫して実施されている。文書化は部分的で、ツールによる強制はない |
| **L3** | 定義・強制 | プラクティスが文書化され、ツール(CI ゲート・レビュー必須化・自動検査)によって強制されている |
| **L4** | 測定・最適化 | 実施状況が定量的に計測され、指標に基づいて継続的に改善されている(閾値の見直し、傾向監視) |

**運用規則:**

- 上位レベルは下位レベルの要件を包含する。例外的に「ツールで強制されているが文書がない」場合は、**強制の根拠が失われたときに再現できない**ため L2 とする(L3 には文書化と強制の両方が必要)。
- 判定は**評価項目単位**で行い、領域スコアへの集約は 4.1 節に従う。
- 中間値は 0.5 刻みで許容する(例: 「文書化済み・強制は一部のみ」= L2.5)。ただし中間値を使う場合は根拠を所見に記録する。
- 「実施しているという証言」だけではレベルを上げない。レベル判定はエビデンス分類(5 章)上の E1〜E3 に基づくことを原則とし、E4(証言)のみに基づく判定は暫定とする。

### 3. 重大度モデル

所見(finding)には次の 5 段階の重大度を付与する。重大度は「その所見を放置した場合のリスク」の尺度であり、成熟度(現状の実力)とは独立に管理する。

| 重大度 | 定義 | 典型例 | 是正期限の目安 |
|---|---|---|---|
| **Blocker** | 監査の続行より対応が優先される事象。現に損害が発生している、または直ちに発生しうる | 有効なシークレットの露出(履歴含む)、既知悪用済み脆弱性を含む依存が本番経路に存在、ライセンス条件の明白な違反状態での配布 | 即時(24〜72 時間) |
| **Critical** | 高い確率で重大インシデント・重大な品質崩壊につながる欠陥 | テスト未実施のままの本番デプロイ経路、レビューなし直接 push の常態化(規制プロファイル)、脆弱性対応プロセスの不在 | 30 日以内 |
| **Major** | 品質・保守性・運用に実害のあるリスク | フレーキーテストの放置による CI 形骸化、依存更新の長期停滞、Runbook 不在(運用対象) | 90 日以内 |
| **Minor** | 改善が望ましいが実害は限定的 | コミットメッセージ規約の不徹底、文書の軽微な陳腐化 | 次期改善サイクル |
| **Info** | 所見ではなく情報。判断材料・良好事例の記録 | 優れたプラクティスの記録、将来リスクの早期示唆 | (期限なし) |

**判定手順:**

1. **初期値の決定** — 影響度 × 顕在化可能性のマトリクスから初期重大度を決める。

   | | 顕在化可能性: 高 | 中 | 低 |
   |---|---|---|---|
   | **影響度: 高** | Critical | Critical | Major |
   | **影響度: 中** | Major | Major | Minor |
   | **影響度: 低** | Minor | Minor | Info |

2. **調整** — 次の要素で最大 ±1 段階調整する: 波及範囲(単一モジュール限定か、リポジトリ全体か)、修復コスト(放置期間に比例して増大するか)、検出可能性(顕在化しても気づけない構造か)。
3. **セキュリティ所見の特則** — CVSS 等の既存スコアリングが利用可能な場合はそれを優先し、本モデルへの対応(9.0 以上 → Blocker/Critical、7.0 以上 → Critical/Major を起点に文脈調整)を所見に明記する。悪用可能性(公知のエクスプロイトの有無、到達可能性)を必ず考慮する。
4. **Blocker の特則** — Blocker は「マトリクスの結果」ではなく列挙的に定義する(上表の典型例に該当するもの、および利用組織が事前に列挙した事象)。発見時は監査プロセスを中断してでも即時報告する(6 章 ステップ4)。

### 4. スコアリングと集約

#### 4.1 領域スコア

- 各評価領域のスコアは、当該領域の全評価項目の成熟度レベルの**算術平均**(小数第 1 位まで)とする。テーラリング(8 章)で除外した項目は分母から除く。
- **重大度キャップ**: 領域内に未解決の Blocker 所見がある場合、当該領域スコアは最大 1.0、Critical 所見がある場合は最大 2.0 に制限する。平均値の高さが致命的所見を覆い隠すことを防ぐためである。

#### 4.2 リポジトリプロファイルと重み

評価対象を次の 3 プロファイルのいずれかに分類し、領域重みを選択する。いずれにも当てはまらない場合はカスタムプロファイルを定義してよいが、重みの根拠をテーラリング記録に残す。

| 領域 | OSSライブラリ | 社内サービス | 規制産業システム |
|---|---|---|---|
| D1 ガバナンスとリポジトリ運営 | 10 | 6 | 6 |
| D2 バージョン管理プラクティス | 10 | 8 | 7 |
| D3 アーキテクチャと設計 | 8 | 10 | 9 |
| D4 実装品質 | 10 | 10 | 8 |
| D5 テストと品質保証 | 12 | 12 | 10 |
| D6 セキュリティ | 10 | 12 | 14 |
| D7 依存関係とサプライチェーン | 12 | 8 | 10 |
| D8 CI/CDとビルド | 8 | 10 | 8 |
| D9 運用性と可観測性 | 3 | 10 | 9 |
| D10 ドキュメントとナレッジ | 10 | 6 | 5 |
| D11 保守性と進化性 | 7 | 6 | 5 |
| D12 コンプライアンスと監査適合性 | 0 | 2 | 9 |
| **合計** | **100** | **100** | **100** |

- **OSSライブラリ**: 不特定多数が利用・貢献する公開ライブラリ/ツール。ガバナンス・文書・サプライチェーンの比重が高く、運用(D9)は利用側の責務のため低い。
- **社内サービス**: 組織内で開発・運用されるサービス。運用性と CI/CD の比重が高い。
- **規制産業システム**: 金融・医療等、規制要件のあるシステム。セキュリティと監査適合性(D12)が必須領域となる。

#### 4.3 総合スコア

総合スコア = Σ(領域スコア × 領域重み) ÷ 100(0.0〜4.0)。

#### 4.4 総合判定

| ランク | 条件 | 解釈 |
|---|---|---|
| **A** | 総合スコア 3.2 以上 | 模範的。他リポジトリの参照実装となりうる |
| **B** | 2.6 以上 | 健全。個別所見の是正で足りる |
| **C** | 2.0 以上 | 要改善。構造的な弱点領域がある |
| **D** | 2.0 未満 | 要抜本改善。改善計画の策定を必須とする |

**ゲーティング規則**(スコアに優先する):

1. 未解決の Blocker 所見が 1 件でもあれば、総合判定は「**不適合(要即時是正)**」に固定する。
2. 未解決の Critical 所見があれば、総合判定の上限は C とする。
3. 規制産業プロファイルで D6・D7・D12 のいずれかが L2 未満の場合、総合判定の上限は C とする。

#### 4.5 スコアの用途と限界

スコアは経年比較(同一リポジトリの改善追跡)と、同一プロファイル内のポートフォリオ比較に用いる。プロファイルを跨ぐ比較、および 0.1〜0.2 程度の差の解釈は意味を持たない。スコアを開発チームの業績指標に転用してはならない(1.3 節)。数値よりも所見と是正の追跡(6 章 ステップ7)を監査の主産物とする。

### 5. エビデンス分類

所見と成熟度判定の根拠となるエビデンスを 4 クラスに分類する。クラスは確信度規則(7.2 節)の入力となる。

| クラス | 名称 | 内容 | 例 |
|---|---|---|---|
| **E1** | 静的成果物 | 作業ツリー内のファイルとして存在する証拠 | 設定ファイル、CI 定義、文書、コード |
| **E2** | VCS 履歴 | Git 履歴から機械的に導出できる証拠 | コミットメッセージ、変更頻度、作者分布、タグ |
| **E3** | プラットフォーム・実行記録 | ホスティング/CI プラットフォームが保持する記録 | PR レビュー履歴、ブランチ保護設定、CI 実行ログ、リリース承認 |
| **E4** | 人的・外部 | インタビュー、実演、外部文書 | 運用手順の実演、外部監査報告書、チームへの聞き取り |

**規則:**

- すべての所見は、少なくとも 1 つのエビデンス参照(パス+行番号、コミット ID、実行記録 ID、聞き取り記録)を必須とする。エビデンスのない所見は起票できない。
- E4 のみに依拠する所見は「暫定」と明示し、Critical 以上の重大度を付けない(E1〜E3 での裏付けを是正確認の条件とする)。
- エビデンスは監査報告書の付属記録として、少なくとも次回監査まで保全する(規制プロファイルでは組織の記録保持規程に従う)。

### 6. レビュープロセス

監査は次の 7 ステップで実施する。各ステップの成果物は次ステップの入力となる。

| # | ステップ | 主な活動 | 成果物 |
|---|---|---|---|
| 1 | スコーピング | プロファイル決定(4.2)、対象リビジョン・期間の固定、テーラリング(8 章) | スコープ定義書、テーラリング記録 |
| 2 | エビデンス収集 | 全履歴付きクローン取得、CI 定義・プラットフォームメタデータの取得、利用可能なエビデンスクラスの確定 | エビデンスインベントリ |
| 3 | 領域別評価 | 第II部の各領域について、評価項目ごとに確認方法を実施し成熟度を判定 | 項目別判定表(根拠付き) |
| 4 | 所見起票 | 付録A のテンプレートで所見を記録。**Blocker 検出時はこのステップを待たず即時報告** | 所見一覧 |
| 5 | スコアリング | 4 章の規則で領域スコア・総合スコア・総合判定を算出 | スコアシート(付録D) |
| 6 | 報告 | 総合判定、領域別の強み/弱み、所見一覧(重大度順)、良好事例、是正提案 | 監査報告書 |
| 7 | フォローアップ | 是正計画の合意、期限追跡、是正確認(必要に応じ部分再評価) | 是正追跡表 |

**原則:**

- ステップ 2 で対象リビジョン(コミット ID)を固定し、以後の評価はすべてそのリビジョンに対して行う。評価中の更新は対象に含めない。
- ステップ 6 の報告書には、所見だけでなく**良好事例**(Info)を必ず含める。監査を懲罰ではなく改善装置として機能させるためである。
- 是正確認は「宣言」ではなくエビデンス(修正コミット、CI 記録)で行う。

### 7. AIエージェント運用プロトコル

本標準は、AI エージェントが監査人(または監査補助)として評価を実施することを前提に設計されている。第II部の各領域にある「AIエージェント向け判断基準」は領域固有の規則であり、本章はそれらに共通する横断規則を定める。

#### 7.1 役割分担 — 機械判定と判断的評価の分離

評価作業を 2 種類に分ける。

- **機械判定可能シグナル**: ファイルの存在・パターン一致・統計量・履歴クエリなど、手順が決定的で結果が検証可能なもの。AI エージェントが一次判定まで行ってよい。
- **判断的評価**: 設計意図の妥当性、文書と実態の一致、組織文脈に依存する適否など。AI エージェントは「暫定判定 + 根拠 + 反証可能性」の形で提示し、人間の確認を経て確定する。

各領域の「AIエージェント向け判断基準」は、この区分に従って「機械判定シグナル」と「判断留保・エスカレーション」を列挙している。

#### 7.2 確信度

すべての所見・判定に確信度を付与する。

| 確信度 | 条件 |
|---|---|
| **High** | E1/E2 の直接エビデンスに基づく機械判定。手順を再実行すれば同じ結果が得られる |
| **Medium** | 複数の間接シグナルからの推定、またはサンプリングに基づく一般化 |
| **Low** | 証拠の**不在**に基づく推定、または本来 E3/E4 を要する事項を E1/E2 のみで判断した場合 |

**規則:**

- Critical 以上の重大度には High 確信度のエビデンスを必須とする。満たせない場合は重大度を維持したまま「**要確認(Unconfirmed)**」として区別して起票し、人間の検証をブロッキング条件にする。
- Low 確信度の判定は、単独では成熟度スコアに反映しない(参考情報として記録する)。

#### 7.3 ハルシネーション防止規則

1. すべての主張にエビデンス参照を付ける(5 章)。参照は**出力前に実在を再確認**する(パスが存在するか、行番号に該当内容があるか、コミット ID が履歴にあるか)。
2. 「一般的には〜のはず」「通常は〜になっている」という形の断定を禁止する。一般論は推奨(ベストプラクティス)の文脈でのみ使う。
3. 探して見つからなかったものは「未検出」と表現し、「存在しない」と断定しない。特にサンプリング(7.4)を行った場合は、探索範囲を必ず併記する。
4. ツール実行結果を引用するときは、実行したコマンドと対象リビジョンを併記する。

#### 7.4 サンプリング規則

- **全数確認が原則の項目**: 単一ファイルの存在・内容で判定できるもの(LICENSE、SECURITY.md、CI 定義、ロックファイル等)。サンプリング不可。
- **サンプリング可の項目**: コード品質・テスト品質など対象が多数のもの。次の 3 系統を併用する。
  1. **ホットスポット抽出**: 直近 12 ヶ月の変更頻度上位ファイル(`git log --since` の集計)
  2. **構造代表抽出**: 各トップレベルモジュール/ディレクトリからサイズ加重で無作為抽出
  3. **直近大型変更**: 直近の大規模差分(リファクタリング・機能追加)から抽出
- サンプル数の目安: 対象母集団の 5% 以上かつ 20 ファイル以上(母集団がそれ未満なら全数)。
- サンプリングを行った判定には、抽出方法・件数・母集団サイズを必ず記録する。

#### 7.5 実行環境の前提と限界

- **full clone 必須**: shallow clone では履歴系判定(D2、D11 ほか)が成立しない。取得できない場合、該当項目は NE(下記 7.6)とする。
- **E3 の可用性**: PR レビュー履歴・ブランチ保護・CI 実行ログが取得できない場合、それらを要する項目は確信度を Medium 以下に降格するか NE とする。E1/E2 の代理シグナル(マージコミットの形状等)で代替する場合は、代理であることを明記する。
- **モノレポ**: コンポーネント境界が明確な場合、第II部の評価をコンポーネント単位に分割して実施し、報告書で統合してよい。分割単位はスコープ定義書に記録する。
- **秘匿領域**: 監査人がアクセスを許可されていない領域(サブモジュール、暗号化ファイル)は NE とし、範囲外であることを報告書に明記する。

#### 7.6 出力契約

- 所見は付録A のテンプレートに従って構造化して出力する(Markdown または JSON)。
- 評価不能な項目は **NE(Not Evaluable)** と判定し、理由(エビデンス不可用・アクセス不可・テーラリング除外)を付す。NE はスコア計算の分母から除くが、NE が領域の項目数の半数を超えた場合は領域スコアを算出せず「評価不能領域」として報告する。
- 判定・所見・スコアの出力に、対象リビジョン(コミット ID)と評価実施日時を必ず含める。

### 8. テーラリング指針

テーラリングとは、対象の性質に応じて評価項目の適用を調整することである。**調整は自由裁量ではなく、記録された決定**でなければならない。

**テーラリング記録の必須フィールド**: 対象項目 ID / 調整内容(除外・目標レベル変更・代替手段の容認)/ 理由 / 承認者 / 見直し期限。

**標準テーラリング(事前定義された調整):**

| 状況 | 調整 |
|---|---|
| リポジトリ年齢 6 ヶ月未満 | 全領域の目標レベルを 1 段階引き下げ(ただし D6-1 シークレット管理と D1-2 ライセンスは引き下げ不可) |
| アーカイブ済み・保守終了宣言済み | D6(既知脆弱性の告知)と D1-2(ライセンス)のみ評価。他は NE |
| ライブラリ型(実行環境を持たない) | D9 は「利用者に運用情報を提供しているか」に読み替え、重みを D5/D7 に振り替え |
| 実験・プロトタイプと明示されたリポジトリ | プロファイル重みではなく「本番転用の歯止め(明示の警告、本番参照の不在)」を D1 で評価し、他は簡易評価 |
| 個人開発・貢献者 1 名 | D2-3(レビュープロセス)は「レビューの代替統制(セルフレビュー手順、CI ゲート強化)」に読み替え |

**テーラリング不可の項目(プロファイル別):**

- 全プロファイル共通: D6-1(シークレット管理)、D1-2(ライセンスと権利表記)
- 規制産業プロファイル: D6・D7・D12 の全項目(緩和には監査主管部門の明示承認を要する)

## 第II部 評価領域

第II部は 12 の評価領域を定義する。各領域は同一の構成を持つ: **評価目的 / 評価項目 / 評価基準 / 確認方法 / 重大度 / よくあるアンチパターン / 推奨ベストプラクティス / 参考標準・出典 / AIエージェント向け判断基準**。

評価項目は `D<領域番号>-<項目番号>` で採番し、監査で生成するチェックリスト・所見はこの ID に遡って紐付ける(1.4 節)。「評価基準」の L0〜L4 アンカーは 2 章の共通スケールを当該領域に具体化したものであり、項目単位の判定に迷った場合の校正点として使う。

### D1. ガバナンスとリポジトリ運営

#### 評価目的

リポジトリの所有・意思決定・参加の規則が明確で、利用者と貢献者が自分の権利・義務・相談先を判断できる状態を保証する。ガバナンスの欠如は個別の技術欠陥より発見が遅く、ライセンス違反・保守停止・属人化として顕在化した時点では修復コストが極大化しているため、独立領域として評価する。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D1-1 | オーナーシップと保守体制の明示 | 責任者・保守チームが機械可読または文書で明示され、実際に活動しているか |
| D1-2 | ライセンスと権利表記 | ライセンスが明示され、第三者コードの権利表記が管理されているか |
| D1-3 | 貢献プロセス | 変更を提案する手順(ブランチ・レビュー・受け入れ基準)が文書化され、実態と一致しているか |
| D1-4 | 行動規範とコミュニティ運営 | 参加者の行動規範と違反時の連絡先・手続が定義されているか(公開・複数組織参加のリポジトリで適用) |
| D1-5 | 意思決定と変更管理の透明性 | 大きな変更(方針・互換性・アーキテクチャ)の提案・合意プロセスが追跡可能か |
| D1-6 | リポジトリ衛生 | アクセス権限の方針、必須ファイルの所在、不要物(ビルド成果物・一時ファイル)の混入防止が管理されているか |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | ライセンス・責任者・貢献手順のいずれも確認できない |
| L1 | LICENSE 等は置かれているが、保守体制・貢献手順は暗黙知。文書と実態が乖離 |
| L2 | 必須ファイル一式が存在し内容が実態と概ね一致。オーナー情報の更新は不定期 |
| L3 | オーナー定義が機械可読(CODEOWNERS 等)でレビュー割当てに使われ、貢献プロセスがツールで強制されている |
| L4 | オーナー情報の鮮度・貢献プロセスの実効性が定期的に棚卸しされ、形骸化が検出・是正されている |

#### 確認方法

- 必須ファイルの存在と内容: LICENSE(または COPYING)、NOTICE(該当時)、README、CONTRIBUTING、CODEOWNERS/MAINTAINERS、CODE_OF_CONDUCT(D1-4 適用時)。
- `git log -1 --format=%ci -- <オーナー定義ファイル>` で最終更新を確認し、直近 12 ヶ月の実コミッター(`git shortlog -sn --since=12.months`)と突合する。
- CONTRIBUTING に書かれた手順(ブランチ名、レビュー、テスト実行)と、直近マージ済み変更の実際の形状を突合する。
- 大きな変更(互換性破壊、方針変更)について、提案記録(RFC/proposal/ADR/Issue)への参照が履歴から辿れるかを確認する。
- ビルド成果物・IDE 設定・OS ゴミファイルの混入を作業ツリーと履歴で確認する(無視設定の有無を含む)。
- アクセス権限・ブランチ保護の方針は E3(プラットフォーム設定)または E4(聞き取り)で確認する。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| 配布・公開されているのにライセンス表記がない/第三者コードの権利表記義務に違反している | Blocker〜Critical |
| オーナー定義が存在しないか、記載者全員が 12 ヶ月以上活動していない | Major(規制プロファイルでは Critical) |
| CONTRIBUTING と実態の乖離、行動規範の連絡先が機能していない | Minor〜Major |
| ビルド成果物の混入、必須ファイルの所在が非標準 | Minor |

#### よくあるアンチパターン

- **「みんなのもの」は誰のものでもない** — オーナー未定義のまま複数チームが変更し、品質責任が消失する。
- **退職者 CODEOWNERS** — オーナー定義が更新されず、レビュー割当てが機能していない。
- **ライセンスのコピペ事故** — 他プロジェクトの LICENSE を著作権者名ごと複製、あるいは依存の再配布条件を確認しないまま同梱。
- **文書だけのガバナンス** — CONTRIBUTING に書かれたプロセスが一度も実施された形跡がない。
- **無言の方針転換** — 互換性方針やサポート範囲が Issue の片隅で変更され、文書に反映されない。

#### 推奨ベストプラクティス

- オーナー定義を機械可読形式(CODEOWNERS 等)で保持し、CI で「全ディレクトリがいずれかのオーナーに割当てられていること」を検証する。
- ライセンス・権利表記は SPDX 識別子と REUSE 仕様に沿って機械検証可能にする。
- 大きな変更は軽量な提案プロセス(RFC/ADR)を通し、提案文書をリポジトリ内に残す。
- 年 1 回以上、オーナー情報・アクセス権限・必須ファイルの棚卸しを行い、棚卸し記録を残す。

#### 参考標準・出典

- OpenSSF Best Practices Badge(旧 CII Best Practices)— 公開プロジェクトの必須ファイル・プロセス要件
- REUSE Specification / SPDX — ライセンス表記の機械可読化
- Contributor Covenant — 行動規範のデファクト標準
- 経済産業省「システム管理基準」— 組織側の管理責任の枠組み

#### AIエージェント向け判断基準

**機械判定シグナル(High 確信度で判定してよい):**

| シグナル | 手順 | 判定 |
|---|---|---|
| ライセンス存在 | ルートの LICENSE/COPYING(および SPDX ヘッダ)を確認 | 不在なら D1-2 は L0。公開リポジトリなら所見(Critical 起点) |
| オーナー定義の鮮度 | オーナー定義ファイルの最終更新日時と `git shortlog -sn --since=12.months` を突合 | 記載者の過半が直近コミッターに現れない場合、形骸化シグナル(Medium — 名寄せの不確実性があるため) |
| 必須ファイル一式 | README / CONTRIBUTING / CODE_OF_CONDUCT / SECURITY.md の存在 | 存在は L1 の必要条件にすぎない。内容の実質は下記の判断的評価へ |
| 不要物混入 | バイナリ・ビルド成果物・IDE 設定の作業ツリー内検出、無視設定の有無 | 検出リストを提示して D1-6 の減点根拠とする |
| 提案プロセスの痕跡 | ADR/RFC/proposal ディレクトリの存在と、直近の大型変更(差分行数上位のマージ)からの参照有無 | 参照ゼロなら D1-5 は L2 以下 |

**判断留保・エスカレーション:**

- ライセンスの互換性・違反の断定は法的判断を含むため行わない。「表記の不在」「条件と配布形態の不一致の疑い」まで(Medium)を報告し、法務確認を推奨事項とする。
- CODEOWNERS の人物が退職済みかどうかは E1/E2 から確定できない。「直近活動なし」という事実のみを報告する。
- ブランチ保護・アクセス権限は E3 が取得できなければ NE とする(マージコミット形状からの推定は D2 で行い、代理シグナルであることを明記)。

### D2. バージョン管理プラクティス

#### 評価目的

Git 履歴そのものを一級の成果物として評価する。履歴は障害調査・変更影響分析・監査証跡の基盤であり、崩れた履歴は事後に修復できない。ブランチ運用・コミット品質・レビュー統制・リリース規律が、追跡可能で改ざんに強い変更記録を作っているかを保証する。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D2-1 | ブランチ戦略の定義と遵守 | ブランチモデルが文書化され、履歴の形状が定義と一致しているか |
| D2-2 | コミットの原子性とメッセージ品質 | 1 コミット 1 意図が守られ、メッセージが変更理由を説明しているか |
| D2-3 | 変更レビュープロセス | 主要ブランチへの変更が第三者レビューを経ているか。自己マージ・直接 push の統制 |
| D2-4 | 履歴の完全性・追跡性 | 変更が課題管理(Issue/チケット)と相互参照でき、履歴書き換えが統制されているか |
| D2-5 | タグ・リリースの規律 | リリースがタグで特定でき、バージョニング規則(SemVer 等)が一貫しているか |
| D2-6 | 機密情報の履歴混入防止 | シークレット・個人データが履歴に混入していないか。混入時の対応手順があるか |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | 履歴が変更記録として機能していない(巨大コミット、無意味なメッセージ、main 直接 push のみ) |
| L1 | ブランチ・PR は使われているが運用は個人差が大きく、規約はない |
| L2 | ブランチモデルとメッセージ規約が慣行として定着。例外(hotfix 直 push 等)が散見される |
| L3 | 規約が文書化され、ブランチ保護・コミットメッセージ検査・レビュー必須化で強制されている |
| L4 | レビューリードタイム・規約逸脱率が計測され、運用が定期的に見直されている |

#### 確認方法

- ブランチ戦略文書(CONTRIBUTING 等)と `git log --graph` の実際の形状(マージ基点、長命ブランチの有無)を突合する。
- `git log --format=%s` の直近 100〜200 件でメッセージ規約適合率・平均差分サイズ・fixup/WIP コミットの残留を確認する。
- レビュー実施率は E3(PR レビュー記録)で確認する。取得不能時はマージコミットの形状と co-author/reviewer トレーラーを代理シグナルとする。
- Issue/チケット参照率をメッセージ・PR 本文から集計する(D12-1 と共用)。
- `git tag` の一覧とバージョニング規則の一貫性、リリースブランチ/タグと CHANGELOG の対応を確認する。
- シークレット走査ツール(例: gitleaks 系)を**全履歴**に対して実行する。作業ツリーだけの走査は不十分である。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| 履歴に有効な可能性のあるシークレットが存在する | Blocker(失効確認まで)。D6-1 と連携 |
| 主要ブランチへのレビューなし変更が常態化 | 規制プロファイルで Critical、他は Major |
| リリースがタグで特定できない/バージョン規則が無い | Major |
| メッセージ規約の不徹底、WIP コミット残留 | Minor |

#### よくあるアンチパターン

- **金曜夜の巨大コミット** — 数千行・複数意図の変更が 1 コミットで入り、レビューも bisect も不能。
- **"fix" "update" の羅列** — メッセージが変更理由を持たず、履歴が grep 不能。
- **承認の形骸化** — レビュー必須設定はあるが、常に同一人物が数分で approve している(E3 で検出)。
- **削除したから大丈夫** — シークレットを後続コミットで削除し、履歴に残ったまま放置。
- **タグの上書き・移動** — 同名タグの付け替えでリリースの同一性が失われる。

#### 推奨ベストプラクティス

- コミットメッセージ規約(例: Conventional Commits)を採用し、CI で機械検査する。規約は「型」より「理由の記述」を重視して定める。
- 主要ブランチはブランチ保護(直接 push 禁止・レビュー必須・CI 必須)を設定し、例外手続(緊急時)を文書化する。
- リリースは注釈付きタグ + 署名(タグ署名またはコミット署名)で行い、タグの不変性を運用規則とする。
- シークレット混入防止をコミット前フック + CI + 定期全履歴走査の三層で構成する。

#### 参考標準・出典

- Conventional Commits 1.0.0 / Semantic Versioning 2.0.0
- Keep a Changelog — リリース記録との対応
- OpenSSF Scorecard(Code-Review, Signed-Releases 該当項目)
- NIST SP 800-218(SSDF)PS.1 — コードの保護・変更統制

#### AIエージェント向け判断基準

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| メッセージ規約適合率 | `git log --format=%s -200` を規約パターン(採用規約が明示されていればそれ、なければ Conventional Commits 型)と照合 | 適合率 80% 以上で L2〜L3 の裏付け。50% 未満は D2-2 減点。規約が独自の場合は文書を優先 |
| コミット原子性 | 直近 200 コミットの差分統計(`git log --shortstat`)で中央値・外れ値を算出 | 変更 1,000 行超のコミットが 10% 超なら原子性の所見候補(リネーム・生成物・ベンダリングを除外してから判定) |
| レビュー代理シグナル | マージコミット比率、PR 番号参照率、reviewer/co-author トレーラー | E3 不在時のみ使用し、確信度は Medium 以下。「レビューが無い」とは断定しない |
| タグ規律 | `git tag --sort=creatordate` の命名一貫性、SemVer 適合、直近リリースとの間隔 | タグ不在・規則混在は D2-5 減点(High) |
| 全履歴シークレット走査 | 走査ツールを全履歴モードで実行 | 検出時は**内容を出力に転記せず**、コミット ID・パス・種別のみ記録して即時エスカレーション(3 章 Blocker 手続)。有効性の確認は人間が行う |
| Issue 参照率 | メッセージ/マージ記録内のチケット ID パターン集計 | 参照率はプロファイル依存で解釈(規制: 80% 以上を L3 目安、OSS: PR 単位で判定) |

**判断留保・エスカレーション:**

- force-push の有無はクローンからは原則確認できない(E3 の監査ログが必要)。「確認不能」と明記する。
- squash マージ運用ではコミット統計が実態(レビュー単位)とずれる。マージ戦略を先に判定し、統計の解釈を切り替える。
- 検出したシークレット様文字列の真偽(有効か、テスト用か)の判定は試行(実際の認証)をしてはならない。形式と文脈からの推定に留め、失効対応は所有者に委ねる。

### D3. アーキテクチャと設計

#### 評価目的

システムの構造が意図を持って設計され、その意図が文書と実装の双方で維持されているかを保証する。アーキテクチャの劣化(境界の崩壊、依存の錯綜、暗黙の契約)は個別のコード欠陥と異なり漸進的に進行し、変更コストの指数的増大として現れる。監査では「現在の構造の良否」だけでなく「構造を維持する仕組みの有無」を評価する。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D3-1 | アーキテクチャの文書化と実装の一致 | 構造(コンポーネント・データフロー・境界)が文書化され、実装と一致しているか |
| D3-2 | モジュール境界と依存方向の規律 | レイヤ/モジュール間の依存規則が定義され、違反(循環依存・レイヤ飛び越し)が統制されているか |
| D3-3 | 設計判断の記録 | 重要な設計判断が理由・代替案・帰結とともに記録されているか(ADR 等) |
| D3-4 | 外部契約の管理 | 公開 API・スキーマ・プロトコルの互換性方針が定義され、破壊的変更が統制されているか |
| D3-5 | 横断的関心事の一貫性 | エラー処理・認証・設定・ロギング等の方式がリポジトリ内で統一されているか |
| D3-6 | データモデルとマイグレーション管理 | 永続データの構造変更が再現可能な手順(マイグレーション)として管理されているか |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | 構造の文書がなく、実装からも一貫した境界が読み取れない |
| L1 | 初期設計文書はあるが更新されておらず、実装との一致が保証されない |
| L2 | 主要な構造文書と ADR が維持され、大きな変更時には概ね更新される |
| L3 | 依存規則・互換性方針が明文化され、ツール(依存検査・契約テスト・スキーマ互換チェック)で強制されている |
| L4 | 構造の健全性(循環、結合度、契約違反)が継続計測され、劣化がトレンドとして管理されている |

#### 確認方法

- アーキテクチャ文書(構成図・データフロー・境界定義)の所在と最終更新を確認し、直近の大型変更が反映されているかを突合する。
- モジュール間依存を言語のビルド情報・import 解析から抽出し、文書化された依存規則(あれば)と照合する。循環依存の有無を確認する。
- ADR(または同等の設計記録)の存在・更新継続性・直近の重要変更との対応を確認する。
- 公開契約(API 定義、スキーマ、プロトコル定義ファイル)の履歴から破壊的変更を抽出し、バージョニング・非推奨化手続(D11-2)との整合を確認する。
- エラー処理・設定読込・認証の実装方式をサンプリングし、方式の混在度を確認する。
- マイグレーションの管理方式(順序保証、ロールバック手順、適用記録)を確認する。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| 公開契約の破壊的変更が予告・バージョニングなしで行われている | Critical |
| 依存規則の不在と循環依存の広範な存在 | Major |
| アーキテクチャ文書の欠落・重大な陳腐化(実装と矛盾) | Major |
| ADR 不在(ただし小規模・単純構造では Minor) | Minor〜Major |
| 横断的関心事の方式混在 | Minor〜Major(混在が障害対応を阻害する構造なら Major) |

#### よくあるアンチパターン

- **考古学文書** — 初期設計書が「あるべき姿」として残り続け、現実と乖離したまま新人を誤導する。
- **なし崩しの密結合** — 「今回だけ」のレイヤ違反 import が繰り返され、境界が実質消滅する。
- **口伝の互換性方針** — 何が公開 API かが暗黙で、利用者は変更のたびに壊れる。
- **共有データベース結合** — モジュール境界を迂回してテーブルを直接参照し、スキーマ変更が全体停止リスクになる。
- **理由なき例外の増殖** — エラー処理方式が書いた人ごとに異なり、障害時のログが解読不能になる。

#### 推奨ベストプラクティス

- 構造文書は「更新され続けられる最小限」に絞る(例: C4 モデルの上位 2 階層 + 境界規則)。詳細は ADR に委ねる。
- 依存規則を機械検査する(言語・ビルドツールの依存検査機構、アーキテクチャテスト)。規則は許可リスト形式が望ましい。
- 公開契約はスキーマファーストで管理し、互換性チェック(後方互換の機械検証)を CI に組み込む。互換性維持期間を明文化する。
- ADR は軽量フォーマット(文脈・決定・帰結)で、重要判断の発生時に必ず 1 枚書く。決定の否定・置換も新しい ADR で記録する。

#### 参考標準・出典

- ISO/IEC/IEEE 42010 — アーキテクチャ記述の概念枠組み
- ISO/IEC 25010:2023 — 保守性(モジュール性・再利用性・解析性)の品質特性定義
- Architecture Decision Records(M. Nygard の原型)/ C4 model — 記録・記述の実務形式
- Semantic Versioning 2.0.0 — 公開契約のバージョニング規約

#### AIエージェント向け判断基準

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| 設計記録の存在と継続性 | ADR/設計文書ディレクトリの検出、件数、最終追加日、直近 12 ヶ月の大型マージとの対応 | 大型変更(差分上位 10 件)のうち設計記録に対応があるのが半数未満なら D3-3 は L2 以下 |
| 循環依存 | 言語標準のビルド/依存解析(利用可能な場合)または import グラフ抽出で強連結成分を検出 | 循環の存在自体は High で報告可。深刻度(意図的か、範囲)は判断的評価 |
| 契約ファイルの破壊的変更 | API/スキーマ定義ファイルの履歴から、フィールド削除・型変更・番号再利用等のパターンを抽出 | 破壊的変更の検出は High。「予告なし」かどうかは CHANGELOG・バージョンタグと突合してから判定 |
| 文書鮮度ギャップ | アーキテクチャ文書の最終更新以降のコード変更量(コミット数・差分行数)を集計 | 文書更新なしで大量変更(目安: 30% 超のファイルが変更)なら陳腐化シグナル(Medium — 変更が構造に無関係の可能性がある) |
| 横断方式の混在度 | エラー処理・設定読込の代表パターンを 2〜3 抽出し、サンプル(7.4)内での分布を集計 | 支配的方式が 70% 未満なら混在の所見候補(Medium) |

**判断留保・エスカレーション:**

- 「アーキテクチャが適切か」(選択された構造の良否)は評価しない。評価するのは**意図の存在・記録・維持機構**である。構造自体への意見は Info(推奨)として分離する。
- 図と実装の一致は全数検証できない。突合したコンポーネント・不一致箇所を明示し、一致率の一般化はサンプル範囲を付して行う。
- モノレポでは境界違反の判定基準がコンポーネント定義に依存する。スコープ定義書の分割単位を先に確認し、未定義なら D3-2 の判定を保留して定義の不在自体を所見とする。

### D4. 実装品質

#### 評価目的

コードが「読む人・変更する人」に対して誠実であるか — 可読性・複雑さの管理・エラー処理の規律 — を保証する。実装品質の低下は欠陥密度と変更リードタイムに直結するが、個々の善し悪しの指摘は無限にありうるため、監査では**品質を維持する体制(規約・自動検査・抑制の統制)**と**構造的な劣化シグナル**に焦点を絞る。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D4-1 | スタイルの一貫性と自動化 | フォーマッタ・リンタが導入され、設定がリポジトリで共有・強制されているか |
| D4-2 | 複雑度の管理 | 過大な関数・深いネスト・巨大ファイルが統制され、ホットスポットが把握されているか |
| D4-3 | 重複の管理 | コピー&ペーストによる実質重複が統制されているか |
| D4-4 | エラーハンドリングの規律 | エラーの握りつぶし・情報喪失がなく、失敗時の挙動方針が一貫しているか |
| D4-5 | 静的解析と抑制の統制 | 静的解析・型検査が有効で、警告抑制(suppress/ignore)が理由付きで管理されているか |
| D4-6 | 命名・コメント・TODO の管理 | 名前とコメントが意図を伝え、TODO/FIXME が追跡されているか |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | スタイル・検査の仕組みがなく、コードの一貫性が読み取れない |
| L1 | 一部にリンタ等はあるが設定が共有されず、実行は任意 |
| L2 | 共有設定が存在しチームは概ね従うが、CI での強制はないか一部のみ |
| L3 | フォーマット・静的解析が CI で強制され、抑制コメントに理由記載が求められる |
| L4 | 複雑度・重複・抑制数が計測され、ホットスポットへの改善が計画的に行われている |

#### 確認方法

- リンタ・フォーマッタ・型検査の設定ファイルの存在と、CI 定義での実行有無・失敗時の扱い(警告のみか、ゲートか)を確認する。
- 抑制コメント(言語慣習の lint 無効化・警告抑制注釈)の密度と理由記載率をサンプルで確認する。
- サンプル(7.4)に対して関数長・ネスト深度・ファイルサイズの分布を測定し、ホットスポット(変更頻度 × サイズ)と重ねる。
- エラー処理をサンプルで確認する: 例外・エラー値の握りつぶし(空 catch、無視される戻り値)、エラー情報の喪失(原因の破棄)、失敗方針(fail-fast/fail-safe)の一貫性。
- 重複検出ツールの結果、または代表的なユーティリティ(バリデーション、日付、HTTP 呼び出し)の実装が何箇所にあるかを確認する。
- TODO/FIXME/HACK の件数と経年(blame による記入時期)を集計し、追跡の仕組み(チケット参照)の有無を確認する。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| エラー握りつぶしが障害の隠蔽につながる箇所(決済・データ整合性・セキュリティ判定)に存在 | Critical |
| 静的解析の広範な抑制(理由なし)、CI ゲートの実質無効化 | Major |
| ホットスポットの複雑度が放置され変更のたびに欠陥が出ている形跡 | Major |
| スタイル不統一、TODO の未追跡 | Minor |

#### よくあるアンチパターン

- **空 catch の墓場** — 例外を握りつぶして「動いているように見える」状態を作り、障害を数ヶ月後に別の場所で顕在化させる。
- **リンタとの休戦協定** — 導入時の警告が多すぎて全体を抑制し、以後新規違反も素通しになる。
- **神クラス/神ファイル** — 変更が集中する巨大ファイルが「触ると壊れる」聖域化する。
- **コピペ増殖** — 「少しだけ違う」実装が並び、修正が常に N 箇所必要になる。
- **嘘をつくコメント** — 実装変更にコメントが追随せず、読み手を積極的に誤導する。

#### 推奨ベストプラクティス

- フォーマットは議論の余地なく自動化(設定の共有 + CI 強制)し、レビューの認知資源を設計と正しさに使う。
- 静的解析は「新規違反ゼロ」方式(ベースライン許容 + 増分ゲート)で導入し、抑制には理由と参照(チケット)を必須にする。
- エラー処理方針(何を握りつぶしてよいか、ログ・再送出・変換の規則)を文書化し、レビュー観点に含める。
- 複雑度・重複の閾値は絶対値の強制より、ホットスポット(変更頻度上位)への集中的改善を計画する。

#### 参考標準・出典

- ISO/IEC 5055:2021 — 信頼性・保守性等のコード品質自動計測(CISQ)
- ISO/IEC 25010:2023 — 保守性・信頼性の品質特性
- Google Engineering Practices(コードレビュー基準)— 可読性・複雑さの審査観点
- 各言語コミュニティの公式スタイルガイド(採用言語のものを監査時に特定して参照する)

#### AIエージェント向け判断基準

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| 検査体制の存在 | リンタ・フォーマッタ・型検査の設定ファイル検出 + CI 定義内での実行ステップ有無 | 設定なし → D4-1/D4-5 は L1 以下。CI 強制なし → L2 以下(High) |
| 抑制密度 | 言語別の抑制注釈パターンを grep し、件数/KLOC と理由記載率を算出 | 目安: 5 件/KLOC 超かつ理由記載率 50% 未満で D4-5 の所見候補(High で事実提示、深刻度は文脈判断) |
| 空 catch・無視戻り値 | 言語別パターン(空の例外ハンドラ、エラー戻り値の破棄)を grep し、ヒットを分類 | 検出は候補に留める(Medium)。決済・認証・整合性経路上のものだけ個別確認して重大度を上げる |
| 複雑度分布 | サンプルに対し関数長・ネスト深度を測定し、分布と外れ値を報告 | 絶対閾値での断罪はしない。ホットスポットとの重なり(変更頻度上位 × 外れ値)のみ Major 候補とする |
| TODO 経年 | TODO/FIXME を grep し、blame で記入時期を取得、チケット参照の有無を分類 | 12 ヶ月超・参照なしの滞留が支配的なら D4-6/D11-1 の減点根拠(High) |

**判断留保・エスカレーション:**

- 命名・コメントの質は文化・言語文脈に依存する。「明白な誤導(実装と矛盾するコメント)」のみ所見にし、好みの指摘はしない。
- 生成コード・ベンダリングされたコードを測定対象から除外してから統計を取る(除外基準を記録)。誤って含めた統計は全面的に無効になる。
- 「複雑だが正当」(アルゴリズムの本質的複雑さ)と「構造の失敗」の区別は判断的評価。複雑度の数値だけで L 判定を下げない。

### D5. テストと品質保証

#### 評価目的

変更の安全性が人の注意力ではなく仕組みで保証されているかを評価する。テストの価値は「存在」ではなく「回帰を検出し、失敗が信頼される」ことにある。監査では、テスト戦略の構造、ゲートとしての実効性、そしてテスト自体の品質(決定性・独立性)を確認する。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D5-1 | テスト戦略と階層構成 | 単体・結合・E2E の役割分担が定義され、実際の構成比が戦略と整合しているか |
| D5-2 | カバレッジの妥当性 | 重要経路(ビジネスロジック・障害分岐)が被覆され、カバレッジが目的をもって運用されているか |
| D5-3 | テストの決定性と独立性 | フレーキーテストが統制され、実行順・環境・時刻への依存がないか |
| D5-4 | 回帰防止の規律 | 欠陥修正時に再現テストが追加される慣行があるか |
| D5-5 | テストデータ・環境の管理 | フィクスチャが管理され、本番データ・実クレデンシャルの流用がないか |
| D5-6 | 品質ゲートとしての運用 | テストが CI で必須化され、失敗時にマージ・リリースが止まるか |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | 自動テストが存在しない、または実行されていない |
| L1 | テストはあるが範囲は断片的で、実行は開発者任せ |
| L2 | 主要機能にテストがあり CI で実行されるが、失敗の扱い・追加の規律は不定 |
| L3 | テスト必須ゲートが強制され、修正時のテスト追加・フレーキー対応が規律化されている |
| L4 | カバレッジ・フレーキー率・実行時間が計測され、テストポートフォリオが継続的に最適化されている |

#### 確認方法

- テストコードの所在・量(実装コードとの比率)・階層構成(単体/結合/E2E の分布)を確認し、テスト戦略文書(あれば)と突合する。
- CI 定義でテストが必須ステップか、失敗時にどう扱われるか(リトライ設定・許容failure)を確認する。
- カバレッジ計測の有無・閾値運用・除外設定を確認する。数値の高低より「重要経路が除外されていないか」を見る。
- 欠陥修正コミット(メッセージ・チケット種別から特定)のうち、テスト変更を伴う割合を集計する。
- フレーキーシグナル: skip/無効化されたテストの件数と経緯、リトライ機構の使用、時刻・乱数・順序依存パターン。
- フィクスチャ内の実データ様パターン(個人情報・実在クレデンシャル)を確認する(D6-1 と共用)。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| テストが CI ゲートになっていない(失敗してもマージ・デプロイ可能) | Critical |
| フィクスチャに本番由来の個人データ・有効クレデンシャル | Blocker〜Critical(D6 と連携) |
| 欠陥修正にテストが伴わない慣行(再発防止の不在) | Major |
| フレーキーテストの放置(無効化の累積、無条件リトライ) | Major |
| カバレッジ計測なし(テスト自体は存在) | Minor〜Major(プロファイル依存) |

#### よくあるアンチパターン

- **緑を買うためのリトライ** — 失敗したら通るまで再実行する設定で、テストが乱数生成器になる。
- **skip の堆積** — 「一時的に」無効化されたテストが数十件溜まり、誰も理由を知らない。
- **カバレッジ演劇** — 閾値を満たすためのアサーションなしテスト・自明コードのテストで数値だけ達成する。
- **E2E 偏重ピラミッドの逆転** — 遅く壊れやすい E2E に依存し、CI が 1 時間超・失敗原因不明が常態化。
- **本番データのコピー** — 「リアルなテストのため」に個人データをフィクスチャへ持ち込む。

#### 推奨ベストプラクティス

- テスト戦略(各階層の目的・範囲・実行タイミング)を 1 ページで文書化し、CI 構成をそれに対応させる。
- フレーキーテストは「即隔離 + チケット化 + 期限付き修理」のプロセスを定義する。無条件リトライは禁止する。
- 欠陥修正 PR には再現テストを原則必須とし、例外はレビューで明示承認する。
- 決定性を設計で確保する: 時刻・乱数・外部 I/O を注入可能にし、同一入力に対する出力固定をテストで担保する。

#### 参考標準・出典

- ISO/IEC/IEEE 29119 — ソフトウェアテストのプロセス・文書・技法
- Test Pyramid(M. Cohn / M. Fowler による解説)— 階層構成の原則
- xUnit Test Patterns(G. Meszaros)— テスト品質・独立性のパターン言語
- Google Testing Blog — フレーキーテスト統制の実務知見

#### AIエージェント向け判断基準

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| テスト存在と規模 | テストファイル規約(言語慣習)で検出し、テスト:実装比・ディレクトリ分布を算出 | テストゼロ → D5 全体 L0(High)。比率の絶対値では判定せず分布を報告 |
| CI ゲート性 | CI 定義を解析し、テストステップの有無・失敗許容設定・必須化を確認 | テストステップなし/失敗許容 → D5-6 は L1 以下(High) |
| 修正時テスト追加率 | 欠陥修正コミット(fix 系パターン + チケット種別)を抽出し、同一変更内のテストファイル変更率を算出 | 50% 以上で L3 目安、20% 未満は D5-4 減点(Medium — squash 運用では PR 単位で再集計) |
| フレーキー兆候 | skip/disable 注釈の件数と blame 経年、sleep・実時刻・乱数のテスト内使用を grep | 事実の提示は High。「フレーキーである」の断定は E3(実行履歴)なしにはしない |
| フィクスチャ実データ | テストデータ内の個人情報様・クレデンシャル様パターン走査 | 検出時は内容を転記せず D6-1 の手続でエスカレーション |
| カバレッジ運用 | カバレッジ設定・閾値・除外リストの検出 | 除外リストに主要ロジックディレクトリが含まれていれば「演劇」シグナル(Medium) |

**判断留保・エスカレーション:**

- カバレッジ数値の適正水準は文脈依存であり、数値単独で L 判定しない。「重要経路の被覆」の評価はサンプルした経路を明示して行う。
- テストの「意味のなさ」(アサーション不在・自明テスト)はサンプル内の具体例を引用して Medium で報告し、一般化はしない。
- 実行時間・フレーキー率の実測は E3 が必要。取得できなければ兆候(上表)のみ報告し NE を明記する。

### D6. セキュリティ

#### 評価目的

リポジトリが攻撃者の視点に耐える基本統制を備えているかを保証する。対象は (a) リポジトリ自体のセキュリティ(シークレット・アクセス)、(b) コードのセキュア設計・実装、(c) 脆弱性を発見・修正し続けるプロセス、の三層である。個別脆弱性の全数列挙は侵入テストの領分であり(1.3 節)、監査は**統制の存在と実効性**を評価する。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D6-1 | シークレット管理 | 平文シークレットが作業ツリー・全履歴に存在せず、混入防止と漏えい時対応が定義されているか |
| D6-2 | 脆弱性報告・対応体制 | 報告窓口(SECURITY.md 等)・対応手順・期限方針が定義され機能しているか |
| D6-3 | セキュア実装の基本統制 | 入力検証・出力エスケープ・危険 API 回避の方針があり、実装に一貫して現れているか |
| D6-4 | 認証・認可・暗号の規律 | 標準的なプロトコル・ライブラリを使用し、独自暗号・検証無効化がないか |
| D6-5 | セキュリティ検査の CI 組込み | SAST・シークレット走査・依存脆弱性検査(D7-2)が継続的に実行されているか |
| D6-6 | 脅威モデルとセキュリティ設計 | 信頼境界・攻撃面が識別され、設計文書に反映されているか(規制・高リスクプロファイルで必須) |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | シークレットの扱いに規律がなく、セキュリティ検査・報告窓口が存在しない |
| L1 | 明白な問題は個人の注意で避けられているが、仕組み・文書はない |
| L2 | 報告窓口・基本方針があり、検査は不定期に実施される |
| L3 | シークレット走査・SAST・依存検査が CI で強制され、対応期限が方針化されている |
| L4 | 検査結果・対応リードタイムが計測され、脅威モデルが変更に追随して更新されている |

#### 確認方法

- シークレット走査を作業ツリーと**全履歴**に対して実行し、検出時は有効性確認・失効の手続に載せる(結果の転記はしない)。`.env` 等のテンプレート化(example ファイル + 実物の無視設定)を確認する。
- SECURITY.md(報告窓口・対応方針・サポート範囲)の存在と、過去の脆弱性対応の実績(修正コミット・アドバイザリ・CHANGELOG 記載)を確認する。
- 危険パターンの走査: 動的コード実行、文字列連結によるクエリ組立、TLS 検証無効化、ハードコードされた暗号鍵・weak hash の使用。ヒットは文脈確認のうえ分類する。
- 認証・認可・暗号の実装が標準ライブラリ/実績あるライブラリに委ねられているか、独自実装がないかをサンプルで確認する。
- CI 定義内のセキュリティ検査ステップ(SAST・シークレット走査・依存検査)と、検出時の扱い(ゲートか通知のみか)を確認する。
- 脅威モデル文書・セキュリティ設計記述(信頼境界、認証境界、データ分類)の有無と鮮度を確認する。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| 有効な(または有効性未確認の)シークレットが履歴・作業ツリーに存在 | Blocker |
| インジェクション可能なパターンが外部入力経路上に存在する疑い | Critical(確証時)/ 要確認として Critical 起票(7.2) |
| TLS 検証無効化・独自暗号・weak hash が本番経路に存在 | Critical |
| 報告窓口の不在(公開リポジトリ)、セキュリティ検査の CI 不在 | Major |
| 脅威モデル不在 | 規制・高リスクで Major、他は Minor |

#### よくあるアンチパターン

- **「あとで消す」ハードコード** — 開発中の実キーがコミットされ、削除後も履歴に残り続ける。
- **検証の一時無効化の恒久化** — 開発時の TLS 検証スキップ・CORS 全開放が本番設定に紛れ込む。
- **枠組みなき手作りサニタイズ** — 場当たりの文字列置換で「対策済み」とし、ライブラリの標準機構を使わない。
- **アラート疲れによる無視** — 依存脆弱性通知が大量に放置され、本当に危険なものが埋もれる。
- **窓口なき公開** — 報告手段がなく、発見者が公開 Issue に脆弱性を書くしかない状態。

#### 推奨ベストプラクティス

- シークレットは注入方式(環境変数・シークレットマネージャ)に統一し、pre-commit フック + CI + 定期全履歴走査の三層で混入を防ぐ。漏えい時の失効手順を事前に文書化する。
- SECURITY.md に報告窓口・初動期限・開示方針・サポート対象バージョンを明記する。
- インジェクション対策は「エスケープの追加」ではなく「安全な API の強制」(パラメタライズ、テンプレートの自動エスケープ)で構造化し、危険 API をリンタで禁止する。
- 脅威モデルは軽量に始め(信頼境界図 + 主要脅威の列挙)、アーキテクチャ変更時の更新を ADR プロセスに連動させる。

#### 参考標準・出典

- OWASP Top 10 / OWASP ASVS — リスク類型と検証要件
- OWASP SAMM 2.0 — セキュリティ活動の成熟度モデル(本領域の L 判定の参照枠)
- NIST SP 800-218(SSDF)— セキュア開発フレームワーク(PO/PS/PW/RV 実践群)
- CWE Top 25 — 実装欠陥の類型
- ISO/IEC 27002 — 組織的統制との接続(D12 と共用)

#### AIエージェント向け判断基準

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| シークレット走査 | 走査ツールを作業ツリー + 全履歴に実行 | 検出時: 値を出力・転記せず、パス/コミット ID/種別のみで即時 Blocker 手続。テスト用ダミーの主張は失効確認まで受け入れない |
| 報告体制 | SECURITY.md 等の存在と必須要素(窓口・期限・範囲)の充足 | 不在は High で D6-2 減点(公開リポジトリでは Major 起点) |
| 危険パターン | 動的実行・文字列連結クエリ・TLS 検証無効化・weak hash のパターン走査 | ヒットは**候補**(Medium)。外部入力との接続(到達可能性)を個別確認できたもののみ Critical 候補に昇格。全ヒットの機械的な Critical 化は禁止 |
| CI 検査組込み | CI 定義内の SAST/シークレット走査/依存検査ステップとゲート性 | ステップ不在 → D6-5 は L2 以下(High) |
| 対応実績 | 脆弱性修正の痕跡(アドバイザリ、CVE 参照、セキュリティ修正コミット)と修正までの期間 | 実績があれば体制の実効性の裏付け(Medium — 母数が観測できないため) |

**判断留保・エスカレーション:**

- **能動的検証の禁止**: 検出したクレデンシャルでの認証試行、疑わしいエンドポイントへの攻撃的入力の送信は行わない。判定は静的根拠に限る。
- **悪用手順の非記載**: 所見には欠陥の所在と根拠を書き、攻撃手順・エクスプロイトの詳細は記載しない。
- 到達可能性(外部入力が当該コードに達するか)の追跡が不完全な場合、重大度を確定せず「要確認(Unconfirmed)」で人間のセキュリティレビューへ引き継ぐ。
- 暗号実装の妥当性(パラメータ・モード選択)は専門レビュー事項。機械判定は「既知の弱いプリミティブの使用」の検出までとする。

### D7. 依存関係とサプライチェーン

#### 評価目的

リポジトリが取り込む外部コード・ビルド基盤を経由するリスクが管理されているかを保証する。現代のソフトウェアはコードの大半を依存として取り込むため、自前コードの品質だけでは全体の信頼性を語れない。依存の宣言・固定・監視・更新のライフサイクル全体と、ビルド成果物の完全性(来歴)を評価する。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D7-1 | 依存宣言とバージョン固定 | 依存が宣言ファイルで管理され、ロックファイル等で再現可能に固定されているか |
| D7-2 | 既知脆弱性の継続検知(SCA) | 依存の既知脆弱性が継続的に検知され、対応の期限方針があるか |
| D7-3 | 依存の鮮度と EOL 管理 | 依存・ランタイムが保守されているバージョンに保たれ、EOL 前に計画的に更新されているか |
| D7-4 | 依存ライセンスの適合 | 依存のライセンスが棚卸しされ、配布形態と矛盾しないことが確認されているか |
| D7-5 | SBOM の生成と提供 | 構成部品表が生成され、利用者・監査者に提供可能か(規制・配布プロファイルで比重増) |
| D7-6 | ビルド来歴と成果物の完全性 | 成果物がどのソース・手順から作られたかが検証可能で、改ざん耐性があるか |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | 依存の全容が把握できない(宣言外の取り込み、ロックなし、手動配置) |
| L1 | 依存は宣言されているが、固定・脆弱性監視は行われていない |
| L2 | ロックファイルが維持され、脆弱性対応は通知ベースで不定期に実施 |
| L3 | SCA・ライセンス検査が CI で強制され、更新・対応期限が方針化されている(自動更新提案の運用を含む) |
| L4 | 依存の鮮度・脆弱性対応リードタイムが計測され、SBOM・来歴が成果物とともに提供される |

#### 確認方法

- 依存宣言ファイルとロックファイルの存在・コミット状況・整合(宣言とロックの乖離)を確認する。
- 宣言外の依存取り込み(ベンダリング、バイナリ直置き、ビルド時の非固定ダウンロード)の有無を確認する。
- SCA の実行箇所(CI ステップ・プラットフォーム機能・自動更新ボット設定)と、検出時の対応記録(更新コミットの頻度・リードタイム)を確認する。
- ランタイム・主要フレームワークのバージョンを EOL 情報と突合する。
- 依存ライセンスの棚卸し記録(ツール出力・NOTICE への反映)と、リポジトリ自身の配布形態との整合を確認する。
- SBOM 生成の仕組み(CI での生成・成果物への添付)と形式(SPDX/CycloneDX)を確認する。
- ビルドの来歴: 成果物署名・provenance 生成(SLSA 対応)・リリースとソースの対応付けを確認する。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| 既知悪用済み(KEV 掲載等)脆弱性を含む依存が本番経路に存在 | Blocker |
| SCA が存在せず、依存更新が長期(12 ヶ月超)停滞 | Critical |
| ロックファイル不在・宣言外取り込み(再現不能ビルド) | Major(規制では Critical) |
| コピーレフト依存と配布形態の矛盾の疑い | Major(法務確認事項として) |
| SBOM・来歴の不在 | プロファイル依存(規制・配布: Major、他: Minor) |

#### よくあるアンチパターン

- **動くから触らない** — 依存を数年固定し、更新が「全取替えの大工事」になってから着手する。
- **通知の墓場** — 自動更新提案・脆弱性通知が数百件放置され、CI ダッシュボードが警告で飽和する。
- **野良バイナリ** — 出所不明の jar/so/exe がリポジトリに直置きされ、誰も再ビルドできない。
- **ビルド時サプライズ** — ビルドスクリプトが最新版を都度ダウンロードし、同じコミットから違う成果物が生まれる。
- **ライセンスは README で見た** — 依存の推移的ライセンスを確認せず、コピーレフト条件が配布物に伝播していることに気づかない。

#### 推奨ベストプラクティス

- すべての依存を宣言 + ロックで管理し、ロックファイルの更新をレビュー対象にする。ビルド時の非固定取得を禁止する。
- 自動更新提案(ボット)+ SCA ゲート + 期限方針(重大度別の対応期限)を組み合わせ、更新を小さく高頻度に保つ。
- ライセンス検査を CI に組み込み、許容ライセンスの許可リストを明文化する。
- 配布物には SBOM と来歴(provenance)を添付し、SLSA のビルドトラックを段階的に引き上げる。

- OpenSSF Scorecard — 依存管理・ピン留め等の自動評価項目
- CIS Software Supply Chain Security Guide — ソース・ビルド・依存・成果物・デプロイの統制
- SPDX / CycloneDX — SBOM 標準形式
- NIST SP 800-218(SSDF)PW.4 / PS.3 — 再利用コードの管理・成果物保護

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| ロック整合 | エコシステム標準のロックファイル存在・コミット状況・宣言との整合 | ロック不在(慣習上あるべきエコシステムで)→ D7-1 は L1 以下(High) |
| 宣言外取り込み | リポジトリ内バイナリ検出、ビルドスクリプト内の非固定 URL 取得パターン | 検出は High で提示。正当性(公式配布物の同梱等)は判断的評価 |
| SCA・更新運用 | ボット設定ファイル・CI 内 SCA ステップの検出、依存更新コミットの頻度集計 | 仕組みなし + 更新停滞 12 ヶ月超 → D7-2/D7-3 減点(High)。停滞のみなら Medium(手動運用の可能性) |
| EOL 突合 | ランタイム・主要依存の宣言バージョンを EOL 情報と照合 | EOL 超過は High。ただし EOL 情報源と参照日を必ず記録する(オフライン環境では NE) |
| SBOM・来歴 | SBOM 生成設定、成果物署名・provenance 生成の CI ステップ検出 | 不在の重大度はプロファイルで切替(上表) |
| ライセンス棚卸し | 依存ライセンス一覧の生成物・NOTICE の網羅性、コピーレフトライセンスの検出 | 検出と分類まで(High)。適合性の結論は出さず法務確認事項として報告 |

**判断留保・エスカレーション:**

- 脆弱性データベース・EOL 情報への照会が監査環境からできない場合、鮮度系の判定は NE とし「仕組みの有無」のみ評価する。
- 「更新すべきか」の判断には互換性コスト・リスク許容度が絡む。監査は停滞の事実と統制の不在を報告し、更新計画の内容には踏み込まない。
- 依存ツリーの深部(推移的依存)の全数解析が環境上不可能な場合、直接依存 + ロックファイルの範囲で判定し、範囲を明記する。

### D8. CI/CDとビルド

#### 評価目的

「コミットから成果物・デプロイまで」の経路が、コード化され・再現可能で・品質ゲートを通ることを保証する。CI/CD は他領域の統制(テスト・セキュリティ検査・依存検査)を強制する実行基盤であり、その信頼性が失われると全領域の L3 以上が成立しない。パイプライン自体のセキュリティも本領域で扱う。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D8-1 | パイプラインのコード化 | ビルド・検査・デプロイ手順がリポジトリ内の定義として管理され、手作業依存がないか |
| D8-2 | ビルドの再現性 | ツールチェーンのバージョンが固定され、同一ソースから同一成果物が得られるか |
| D8-3 | 品質ゲートの構成 | lint・テスト・セキュリティ検査が必須ゲートとして構成され、所要時間が実用的か |
| D8-4 | デプロイ自動化と昇格統制 | 環境分離(開発/検証/本番)と昇格手続(承認・自動判定)が定義されているか |
| D8-5 | パイプラインのセキュリティ | シークレットの扱い・権限の最小化・サードパーティ部品(アクション/イメージ)の固定がされているか |
| D8-6 | 開発者の再現手段 | CI と同等の検証をローカルで実行できる単一入口(Make 等のタスク定義)があるか |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | ビルド・デプロイが個人の手順書(または記憶)に依存している |
| L1 | CI はあるが範囲が断片的で、成功が必須ではない |
| L2 | 主要な検証が CI で実行されるが、再現性・ゲート性に穴がある |
| L3 | ゲートが必須化され、ツールチェーン固定・環境分離・昇格手続が定義されている |
| L4 | パイプラインの所要時間・失敗率・デプロイ頻度が計測され、継続的に改善されている |

#### 確認方法

- CI/CD 定義ファイルの存在・網羅範囲(ビルド・テスト・検査・デプロイ)と、定義外の手作業手順の有無(README・Runbook との突合)を確認する。
- ツールチェーンのバージョン固定(バージョン指定ファイル、コンテナイメージのダイジェスト固定、ビルドツールの lock)を確認する。
- ゲート構成: どのステップが失敗時にブロックするか、スキップ条件、必須チェックの設定(E3)を確認する。
- デプロイ定義から環境の分離・昇格条件(手動承認・自動判定)・ロールバック手段を確認する。
- パイプライン内のシークレット参照方式(注入か、平文か)、権限スコープ、サードパーティ部品の固定方式(タグかダイジェストか)を確認する。
- ローカル実行の単一入口(タスク定義ファイル)と CI 定義の対応(同じコマンドを呼んでいるか)を確認する。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| デプロイが再現不能な手作業(本番反映が個人依存) | Critical |
| パイプライン内の平文シークレット、過剰権限 | Critical(露出があれば Blocker、D6-1 連携) |
| サードパーティ部品の非固定(改ざん取込みリスク) | Major(規制では Critical) |
| ゲートのスキップ常態化(必須チェックの回避経路) | Major |
| ローカル再現手段の不在 | Minor |

#### よくあるアンチパターン

- **職人の本番反映** — 特定個人の端末からしかデプロイできず、その人の休暇が可用性リスクになる。
- **最新タグの賭博** — ビルドイメージ・アクションを浮動タグで参照し、ある朝突然ビルドが壊れる(または汚染される)。
- **赤いまま進むパイプライン** — 失敗が常態化した必須でないチェックが並び、信号として機能しない。
- **CI だけが知っている** — ビルド手順が CI 定義の中に埋もれ、ローカルでは誰も再現できない。
- **デプロイキーの万能化** — パイプラインに本番全権のクレデンシャルが渡され、侵害時の爆発半径が最大化する。

#### 推奨ベストプラクティス

- 「ローカルのタスク定義を CI が呼ぶ」構造にし、CI 固有ロジックを最小化する(再現性と開発者体験の同時達成)。
- ツールチェーン・ビルド部品はダイジェスト/正確なバージョンで固定し、更新は自動提案 + レビューで行う。
- ゲートは「少数・高速・必須」を原則に設計し、遅い検査は並列化・段階化する(必須でない検査を放置しない)。
- パイプラインの権限は環境ごとに分離した最小権限とし、本番昇格には明示の承認記録を残す(D12-5 連携)。

#### 参考標準・出典

- DORA / Accelerate — デプロイ頻度・リードタイム・変更失敗率・復旧時間の 4 指標
- Continuous Delivery(J. Humble / D. Farley)— パイプライン設計の原則
- SLSA v1.0 Build Track — ビルド環境の完全性レベル
- CIS Software Supply Chain Security Guide — パイプライン統制

#### AIエージェント向け判断基準

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| パイプライン網羅 | CI 定義を解析し、ビルド/テスト/静的検査/セキュリティ検査/デプロイの各段階の有無をマッピング | 定義不在 → D8-1 は L0〜L1(High)。段階の欠落は該当領域(D5/D6)と相互参照 |
| 部品固定 | アクション・イメージ・ツールチェーン参照を抽出し、固定方式(ダイジェスト/正確版/浮動タグ)を分類 | 浮動タグ比率を High で提示。重大度はプロファイルで切替(上表) |
| 平文シークレット | CI 定義・スクリプト内のクレデンシャル様文字列走査(D6-1 と同一手続) | 検出時は D6-1 の Blocker 手続 |
| ローカル/CI 対応 | タスク定義ファイルの存在と、CI 定義がそれを呼んでいるかの突合 | 対応があれば D8-6 の L2〜L3 裏付け(High) |
| ツールチェーン固定 | バージョン指定ファイル(エコシステム慣習)・コンテナ定義のバージョン指定を確認 | 未固定(範囲指定・latest)は D8-2 減点(High) |
| デプロイ統制 | デプロイ定義内の環境分岐・承認ステップ・ロールバック手段の有無 | 定義から読める範囲は High。実運用の承認実績は E3 必要 → なければ Medium |

**判断留保・エスカレーション:**

- パイプラインの**実行実績**(成功率・所要時間・スキップの頻度)は E3 が必要。定義の解析だけで「運用されている」と断定しない(最終実行の痕跡がなければ「定義のみ存在」と報告)。
- ビルド再現性の完全な検証(2 回ビルドしてバイナリ一致)は監査環境で実行可能な場合のみ行い、実行した場合はコマンドと結果を記録する。実行できない場合は固定状況からの推定(Medium)に留める。
- 「手作業デプロイの存在」は E1/E2 から断定できない(定義外の経路は見えない)。Runbook・README の記述との矛盾を根拠に E4(聞き取り)へ引き継ぐ。

### D9. 運用性と可観測性

#### 評価目的

このリポジトリのソフトウェアが「動かし続けられ、壊れたときに分かり、直せる」設計になっているかを保証する。運用性は本番障害の検出時間・復旧時間を直接左右する。ライブラリ型リポジトリでは本領域をテーラリング(8 章)で読み替える。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D9-1 | ログの設計 | ログが構造化され、レベル運用・機微情報の混入防止が規律化されているか |
| D9-2 | メトリクスとヘルスチェック | 稼働状態が外部から機械的に確認でき、主要指標が計測可能か |
| D9-3 | トレースと相関 | 分散処理・非同期処理で要求の追跡(相関 ID・トレース)が可能か(該当構成で適用) |
| D9-4 | Runbook と障害対応 | アラート・障害類型に対応する手順書があり、実際の障害で更新されているか |
| D9-5 | 設定管理の規律 | 設定が環境から注入され、環境別差分が宣言的に管理され、シークレットと分離されているか |
| D9-6 | バックアップ・リストア・アップグレード | データ保全と版更新の手順が文書化され、検証(リストア演習)されているか(状態を持つシステムで適用) |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | 運用に必要な情報(ログ設計・手順・設定方法)が実装からも文書からも得られない |
| L1 | printf 的なログと個人メモで運用されている |
| L2 | 構造化ログ・ヘルスチェック・基本手順書があるが、網羅性・鮮度は不定 |
| L3 | 可観測性の設計方針が文書化され、Runbook がアラートと対応付き、設定・シークレット分離が強制されている |
| L4 | 障害対応の学び(ポストモーテム)が Runbook・設計に還流し、可観測性がコスト含めて最適化されている |

#### 確認方法

- ログ実装をサンプルで確認する: 構造化(機械可読形式)か、レベルの使い分け、個人情報・シークレットの出力有無、相関 ID の伝搬。
- ヘルスチェック・メトリクス公開の実装(エンドポイント・計測ライブラリの使用)と、その文書化を確認する。
- Runbook・障害対応手順の所在・網羅範囲(どの障害類型をカバーするか)・最終更新と、直近の障害対応(修正コミット・ポストモーテム記録)との対応を確認する。
- 設定の注入方式(環境変数・設定ファイル・フラグ)、環境別差分の管理方式、設定例ファイルの提供、シークレットとの分離を確認する。
- バックアップ・リストア・アップグレード手順の文書と、検証の記録(演習・テスト)を確認する。
- デバッグ残骸(標準出力への printf、コメントアウトされたログ)の密度をサンプルで確認する。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| ログに個人情報・シークレットが出力される実装 | Critical(規制では Blocker 相当の扱いを検討) |
| 状態を持つシステムでリストア手順が存在しない/未検証 | Critical |
| Runbook 不在(運用対象)、ヘルスチェック不在 | Major |
| 設定のハードコード(環境別ビルドが必要な構造) | Major |
| デバッグ残骸、ログレベルの無秩序 | Minor |

#### よくあるアンチパターン

- **printf 考古学** — 障害時に grep するのは前任者のデバッグ痕跡で、必要な情報は出ていない。
- **全部 ERROR** — レベルが意味を持たず、アラートが常時発報 → 全員が通知を無視する。
- **Runbook という名の希望** — 手順書はあるが 3 年前のもので、書かれたコマンドはもう存在しない。
- **バックアップはある(はず)** — 取得はされているがリストアは一度も試されておらず、必要になった日に初めて失敗が判明する。
- **ログで漏れる** — 認証トークン・個人情報がデバッグログに出力され、ログ基盤が事実上の漏えい経路になる。

#### 推奨ベストプラクティス

- ログ設計方針(形式・レベル基準・禁止事項・相関 ID)を文書化し、機微情報のマスキングを実装層で強制する。
- ヘルスチェックは「生存」と「依存先込みの準備完了」を区別して提供し、文書化する。
- Runbook はアラート定義と 1:1 で対応付け、障害対応のたびに更新する(ポストモーテトの標準項目に「Runbook 更新」を入れる)。
- リストア・アップグレードは定期演習をスケジュールし、演習記録を残す。設定は 12-Factor の原則(環境からの注入)に従う。

#### 参考標準・出典

- Google SRE Book — 可観測性・Runbook・ポストモーテムの実務標準
- The Twelve-Factor App — 設定・ログの取り扱い原則
- ITIL 4 — インシデント・問題管理との接続
- ISO/IEC 25010:2023 — 信頼性(回復性)・保守性(解析性)の品質特性

#### AIエージェント向け判断基準

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| 構造化ログ | ログライブラリの使用・出力形式設定の検出、printf 的出力との比率(サンプル) | 構造化の仕組みなし → D9-1 は L1 以下(High)。比率は Medium(サンプル依存) |
| 機微情報のログ出力 | ログ出力呼び出し周辺の個人情報・トークン様変数のパターン走査 | ヒットは**候補**(Medium)として個別確認。確認できたもののみ Critical 候補 |
| ヘルスチェック | ヘルスエンドポイント・稼働確認手段の実装パターンと文書の検出 | 運用対象で不在 → D9-2 減点(High) |
| Runbook 鮮度 | 運用文書の存在・最終更新と、直近の障害修正コミット(hotfix 系)との時系列突合 | 障害対応が続いているのに運用文書が長期未更新なら形骸化シグナル(Medium) |
| 設定注入 | 設定例ファイルの存在、ハードコードされた環境依存値(ホスト名・接続文字列)の走査 | ハードコード検出は High(値がプレースホルダか実物かを分類してから) |
| 手順の実在性 | Runbook 内のコマンド・パスを抽出し、リポジトリ内の実在と突合 | 存在しないコマンド・パスへの参照が多ければ陳腐化の High 根拠 |

**判断留保・エスカレーション:**

- アラート設定・ダッシュボード・実際の監視運用は多くの場合リポジトリ外(E3/E4)にある。リポジトリ内から見えない場合は NE とし、「実装側の対応(計測点の提供)」のみを判定する。
- リストア演習・障害対応の実績は E4 で確認する事項。文書の存在だけで L3 を与えない(「文書あり・検証記録なし」は L2.5 上限)。
- ライブラリ型リポジトリでは本領域を 8 章の読み替え(利用者への運用情報提供)で評価し、読み替えたことを判定に明記する。

### D10. ドキュメントとナレッジ

#### 評価目的

リポジトリに関する知識が「人の頭の中」ではなく、発見可能で信頼できる文書として存在するかを保証する。文書の価値は量ではなく、**正しさ(実態との一致)と到達可能性(必要なときに見つかる)**で決まる。本領域は文書の体系と鮮度維持の仕組みを評価し、設計文書の内容の妥当性は D3 で扱う。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D10-1 | README の完全性 | 目的・前提・セットアップ・基本的な使い方が README から辿れ、初見者が最初の一歩を踏み出せるか |
| D10-2 | 開発環境構築手順の再現性 | 環境構築手順が実行可能な形で文書化され、実際に再現できるか |
| D10-3 | 文書体系と索引性 | 文書が体系化(入門/手順/リファレンス/背景の区分)され、入口から目的の文書に到達できるか |
| D10-4 | CHANGELOG・リリースノート | 利用者視点の変更記録が維持され、リリースと対応しているか |
| D10-5 | 鮮度維持の仕組み | 文書の陳腐化を検出・防止する仕組み(doc-as-code、CI でのリンク検査・鮮度検査)があるか |
| D10-6 | 知識の重複と単一情報源 | 同じ情報が複数箇所で矛盾しておらず、正となる場所が定まっているか |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | README が実質空。文書から得られる情報がない |
| L1 | 初期に書かれた文書があるが更新されておらず、信頼できるかが判別不能 |
| L2 | 主要文書(README・セットアップ・変更記録)が維持され、概ね実態と一致 |
| L3 | 文書がコードと同じレビュー・CI プロセスで管理され、リンク切れ・陳腐化の機械検査がある |
| L4 | 文書の利用実態・不足がフィードバックループ(新人オンボーディング、問い合わせ分析)で継続改善されている |

#### 確認方法

- README を初見者の視点で読み、目的の説明 → 前提 → セットアップ → 最初の実行、が途切れず辿れるかを確認する。
- セットアップ手順のコマンドを抽出し、実行可能性を確認する(監査環境で再現可能な場合は実際に実行し、所要時間と失敗点を記録する)。
- 文書の構成(ディレクトリ・索引)と、種類の区分(チュートリアル/ハウツー/リファレンス/解説)の意図が読み取れるかを確認する。
- CHANGELOG の存在・粒度(利用者視点か、コミットログの複写か)・リリースタグとの対応を確認する。
- 文書検査の仕組み(リンクチェック、文書 CI、レビュー必須化)の有無を確認する。
- 同一情報(セットアップ手順、設定一覧など)の重複箇所を検索し、矛盾の有無を確認する。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| セットアップ手順が再現不能(記載コマンド・前提が現状と乖離) | Major |
| README 実質不在(公開・複数チーム利用リポジトリ) | Major |
| 変更記録の不在(配布物があるのに利用者が変更を追えない) | Major(内部ツールでは Minor) |
| 文書間の矛盾(どちらが正か判別不能) | Minor〜Major(運用手順の矛盾は Major) |
| リンク切れ・軽微な陳腐化 | Minor |

#### よくあるアンチパターン

- **希望的 README** — 構想段階の機能が現在形で書かれ、初見者が存在しない機能を探す。
- **オンボーディング口伝** — 環境構築は「隣の人に聞く」が正式手順で、文書は誰も信じていない。
- **コミットログ転写 CHANGELOG** — 内部実装の羅列で、利用者は影響が判断できない。
- **Wiki 分裂** — リポジトリ外の Wiki・共有ドライブに文書が分散し、どれが最新か誰も知らない。
- **書いたら終わり** — 文書に所有者・見直し契機がなく、陳腐化が構造的に放置される。

#### 推奨ベストプラクティス

- 文書はコードと同じリポジトリ・同じレビューで管理し(doc-as-code)、変更に文書更新を含めることをレビュー観点にする。
- 文書体系に意図的な区分(例: Diátaxis の 4 分類)を導入し、入口(README)から各文書への導線を維持する。
- CHANGELOG は利用者影響(追加/変更/非推奨/削除/修正/セキュリティ)で記述する(Keep a Changelog 形式)。
- リンク検査・書式検査・(可能なら)手順の実行検査を CI に組み込む。リポジトリ外に文書を置く場合は「正はどちらか」を明文化する。

#### 参考標準・出典

- Keep a Changelog 1.1 — 変更記録の形式
- Diátaxis — 文書の 4 区分(チュートリアル/ハウツー/リファレンス/解説)
- Google developer documentation style guide — 技術文書の記述標準
- Write the Docs コミュニティの実務知見 — doc-as-code の運用

#### AIエージェント向け判断基準

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| README 構成 | README の見出し構造を解析し、目的/前提/セットアップ/使用法の要素充足を判定 | 要素の欠落は High で提示。「初見者が理解できるか」は判断的評価(Medium) |
| 手順の実在性 | セットアップ手順からコマンド・ファイル参照を抽出し、リポジトリ内の実在(タスク定義・スクリプト・パス)と突合 | 存在しない参照が複数あれば陳腐化の High 根拠。実行検証まで行えた場合はその結果を優先 |
| CHANGELOG 対応 | CHANGELOG のバージョン見出しと `git tag` の突合 | タグにあるのに記録がないリリースが続けば D10-4 減点(High) |
| リンク検査 | 文書内の相対リンク・アンカーの解決検査 | 機械検査そのもの。結果を High で提示 |
| 鮮度ギャップ | 主要文書の最終更新と、参照先コード領域の変更量の突合(D3 と同手法) | ギャップは陳腐化の**兆候**(Medium)。内容確認したものだけ所見に昇格 |
| 重複検出 | セットアップ・設定説明等の重複箇所を検索し、差分を提示 | 矛盾の存在は High(両方の記述を引用)。どちらが正かの判定はしない |

**判断留保・エスカレーション:**

- 文書の「分かりやすさ」は評価しない(読者の前提知識に依存する)。評価するのは充足・一致・到達可能性である。
- セットアップの実行検証は環境影響(パッケージインストール・ネットワーク)を伴う。監査環境のサンドボックス内でのみ実施し、対象環境を汚染する検証は行わない。
- リポジトリ外の文書(Wiki 等)は取得できなければ NE。リポジトリ内からの参照リンクの有効性のみ判定する。

### D11. 保守性と進化性

#### 評価目的

このリポジトリが「これからも変更し続けられる」状態にあるかを評価する。他領域が現在の統制を見るのに対し、本領域は**時間軸**を見る: 負債が管理されているか、知識が分散しているか、変更コストが増大傾向にないか。衰退は突然ではなく、監査で検出可能な傾向として現れる。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D11-1 | 技術的負債の可視化と管理 | 負債が記録され(場所・理由・影響)、返済が計画に載っているか |
| D11-2 | 非推奨化・削除の規律 | 機能・API・コードの廃止が手順(予告・移行期間・削除)として運用され、デッドコードが統制されているか |
| D11-3 | プラットフォーム追随 | ランタイム・フレームワークの大版更新に計画的に追随しているか(D7-3 の脆弱性視点に対し、本項は変更コスト視点) |
| D11-4 | 変更コストの傾向 | ホットスポットの改善・悪化傾向、変更の影響範囲が管理されているか |
| D11-5 | 知識の分散(バス係数) | 主要領域の変更が特定個人に依存していないか |
| D11-6 | 継続的リファクタリング | 構造改善が変更活動の一部として継続しているか(テスト同伴で) |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | 負債・廃止・追随の概念がなく、コードは追加される一方 |
| L1 | 問題は個人が認識しているが、記録・計画はない |
| L2 | 負債・廃止が記録され、返済・削除がときどき実施される |
| L3 | 負債管理・非推奨化手順が定義され、返済がリリース計画に組み込まれている |
| L4 | 変更コスト・知識分散の指標が計測され、悪化傾向への介入が制度化されている |

#### 確認方法

- 負債の記録方式(チケット・TODO 規約・負債台帳)と、記録された負債の返済実績(クローズ率・経年)を確認する。
- 非推奨化の手順(予告方法・移行期間・削除基準)と、deprecated マーカーの滞留期間、デッドコード(到達不能・参照ゼロ)の存在を確認する。
- ランタイム・主要フレームワークの版と、過去の大版更新の実績(更新コミット・所要期間)を確認する。
- ホットスポット分析: 変更頻度上位ファイルのサイズ・複雑度の経年変化(改善/悪化)を確認する。
- 作者分布: 主要ディレクトリごとのコミット作者の集中度を確認する(個人評価に転用しないこと — 1.3 節)。
- リファクタリングコミットの存在・頻度と、テスト変更の同伴率を確認する。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| 中核領域のバス係数が 1(代替者不在)かつ文書も不在 | Major(規制・長期運用前提では Critical) |
| EOL 済みプラットフォーム上での稼働継続(D7-3 と連携) | Critical |
| ホットスポットの構造悪化が継続(変更のたびに肥大) | Major |
| 非推奨のまま数年放置された API・機能 | Minor〜Major(利用者があるなら Major) |
| TODO・デッドコードの堆積 | Minor |

#### よくあるアンチパターン

- **負債の口約束** — 「あとで直す」がコメントにも チケットにも残らず、次の担当者は意図的な手抜きと事故を区別できない。
- **消せない機能** — 利用実態不明の機能が「誰か使っているかも」で残り続け、全変更の検証コストに上乗せされる。
- **大版更新の先送り複利** — 1 版の追随を怠り、次の更新が 2 版分の破壊的変更を一括で浴びる。
- **一人メンテナの沈黙** — 中核モジュールを一人が守り続け、その負荷とリスクが表面化しない。
- **リファクタリング禁止文化** — 「動いているものに触るな」が公式化し、構造改善が事実上不可能になる。

#### 推奨ベストプラクティス

- 負債は発生時に記録する(チケット化、または追跡可能な TODO 規約)。返済枠(容量の一定割合)を計画に確保する。
- 非推奨化は「予告(マーカー + 変更記録)→ 移行期間 → 削除」の 3 段階を規約化し、期間をプロファイル(利用者の広さ)に応じて定める。
- プラットフォーム追随は EOL カレンダーからの逆算で計画する(D7-3 と共通の台帳でよい)。
- 知識分散は仕組みで作る: レビューのローテーション、ペア作業、中核領域の設計文書化(D3・D10 連携)。

#### 参考標準・出典

- Accelerate / DORA — 変更リードタイムと組織能力の関係
- ISO/IEC 25010:2023 — 保守性(修正性・試験性)/ ISO/IEC 5055 — 保守性の自動計測
- Managing Technical Debt(SEI: Kruchten, Nord, Ozkaya)— 負債管理の枠組み
- Refactoring(M. Fowler)— 継続的構造改善の実務原則

#### AIエージェント向け判断基準

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| 作者集中度 | `git shortlog -sn --no-merges --since=24.months -- <主要ディレクトリ>` で領域別の作者分布を算出 | 上位 1 名が 80% 超の領域を列挙(High で事実提示)。bot・squash 運用・移籍を考慮し、バス係数の**結論**は E4 確認へ。個人名は報告書では役割表記に置換 |
| ホットスポット傾向 | 変更頻度上位ファイルのサイズ・(可能なら)複雑度を過去時点と比較 | 継続的肥大は High で提示。「悪化」の判定は正当な成長(機能追加)との区別が必要なため Medium |
| deprecated 滞留 | 言語慣習の非推奨マーカーを grep し、blame で付与時期を取得 | 24 ヶ月超の滞留が支配的なら D11-2 減点(High) |
| デッドコード候補 | 参照解析(利用可能な場合)・エクスポートされていない未参照シンボルの検出 | **候補**として Medium。動的参照・外部利用の可能性があるため削除可能とは断定しない |
| 追随実績 | ランタイム版の宣言と、過去の大版更新コミットの間隔 | EOL 突合は D7-3 と共用。更新間隔の事実は High |
| リファクタリング継続性 | refactor 系コミットの比率とテスト同伴率(D5-4 と同手法) | 比率ゼロが長期間続けば D11-6 の兆候(Medium — squash 運用では PR 単位) |

**判断留保・エスカレーション:**

- 作者統計は**個人評価に転用しない**(1.3 節)。報告書には個人名でなく「特定 1 名への集中」という構造情報として記載し、生データの取り扱いを監査主管の規程に従わせる。
- 負債の「意図的な許容」(スタートアップ期の速度優先など)は経営判断でありうる。監査は記録と可視化の有無を評価し、許容判断の当否は評価しない。
- 「変更コストが増大している」の直接測定にはチケット・工数データ(E3/E4)が要る。E1/E2 からは代理指標(上表)に留め、その旨を明記する。

### D12. コンプライアンスと監査適合性

#### 評価目的

規制・契約・社内規程が要求する統制を、このリポジトリが**証明可能な形で**満たせるかを保証する。技術的に良いシステムでも、証跡が再構成できなければ監査対応・インシデント調査・法的照会に耐えない。本領域は**条件付き領域**である: 規制産業プロファイルでは必須、社内サービスでは限定適用、OSS ライブラリでは原則対象外(4.2 節の重み 0)。

#### 評価項目

| ID | 項目 | 評価する内容 |
|---|---|---|
| D12-1 | 変更のトレーサビリティ | 要求(チケット・課題)→ 変更(コミット・PR)→ リリース(タグ・デプロイ)の連鎖が双方向に追跡できるか |
| D12-2 | 監査証跡の設計 | システムが生成する業務証跡(操作ログ等)が、改ざん耐性・保持期間を考慮して設計されているか |
| D12-3 | データ保護の設計 | 個人データ・機微データの分類・保持・削除の方針が設計と文書に反映されているか |
| D12-4 | 規制要件マッピング | 該当規制・ガイドラインの要求事項と、実装・統制の対応関係が文書化されているか |
| D12-5 | リリース統制と職務分離 | 本番反映に承認・職務分離(開発者単独で本番変更を完結できない)・緊急時手続が定義されているか |
| D12-6 | 記録の保持と時点再現 | 特定時点のシステム状態(コード・設定・依存)を再構成でき、記録が保持規程に従って残るか |

#### 評価基準

| レベル | この領域でのアンカー |
|---|---|
| L0 | 変更とその理由・承認の対応が事後に再構成できない |
| L1 | 追跡は部分的に可能だが、人手の照合作業を要し、抜けが多い |
| L2 | チケット参照・タグ運用が慣行化し、主要な変更は追跡できる |
| L3 | トレーサビリティ・承認・職務分離がツールで強制され、規制マッピングが維持されている |
| L4 | 統制の実効性が内部監査・自己点検で定期検証され、規制変更への追随プロセスがある |

#### 確認方法

- 直近のリリースを 1 つ選び、逆方向トレース(リリース → 含まれる変更 → 各変更の理由・承認)を実際に実施して、途切れる箇所を特定する(最も実効的な検査)。
- コミット・PR のチケット参照率(D2-4 の集計を利用)と、参照先の実在・照合可能性を確認する。
- 業務証跡の設計文書(何を・どこに・どの期間・どんな改ざん耐性で記録するか)と実装の対応を確認する。
- データ分類・保持・削除の方針文書と、スキーマ・実装(保持期限処理、削除機能)の対応を確認する。
- 規制マッピング文書(要求事項 ↔ 実装・統制の対応表)の存在・網羅性・鮮度を確認する。
- リリース手続の定義(承認者・職務分離・緊急変更の事後承認)と、実績記録(E3)を突合する。
- 過去時点の再現可能性: 任意のリリースタグから、当時のコード・設定・依存(ロック)が特定できるかを確認する。

#### 重大度

| 所見の類型 | 重大度の目安 |
|---|---|
| 規制対象の業務証跡が欠落・改ざん可能(要件があるのに設計されていない) | Critical〜Blocker(規制違反が現実化していれば Blocker) |
| 本番変更が開発者単独で完結できる(職務分離要件があるのに) | Critical |
| リリースからの変更追跡が再構成不能 | Critical(規制)/ Major(社内) |
| 規制マッピングの不在・重大な陳腐化 | Major |
| データ保持・削除方針と実装の乖離 | Major〜Critical(個人データの過剰保持は規制次第で Critical) |

#### よくあるアンチパターン

- **監査前夜の考古学** — 監査のたびに数週間かけて証跡を手作業で再構成し、翌年また忘れる。
- **チケット番号だけの儀式** — 参照は付いているがチケットに中身がなく、追跡が形式だけ成立している。
- **消せないログ・消えるログ** — 保持期間の設計がなく、必要なログが消え、消すべき個人データが残る。
- **緊急変更の常態化** — 例外手続(承認スキップ)が使いやすすぎて、統制の主経路になっている。
- **マッピングの初版主義** — 導入時に作った対応表が更新されず、規制改定にもシステム変更にも追随していない。

#### 推奨ベストプラクティス

- トレーサビリティは開発フローに埋め込む(チケット参照の機械検査、リリースノートの自動生成)。「監査用の別作業」にしない。
- 業務証跡は設計文書(記録項目・保持・アクセス制御・改ざん耐性)を先に定め、実装・テストをそれに対応付ける(D3-6・D5 連携)。
- 規制マッピングは要求事項単位で管理し、対応する統制・実装・検証方法・最終確認日を持たせる。規制改定とシステム変更の両方を更新契機として定義する。
- 緊急変更手続には事後レビューの期限と記録を必須化し、利用頻度を計測する(高頻度なら主経路の設計不備)。

#### 参考標準・出典

- ISO/IEC 27001 附属書A — 運用・アクセス・記録の統制
- 経済産業省「システム監査基準」「システム管理基準」— 日本の企業システム監査の基礎枠組み
- COBIT — IT ガバナンスの統制目標
- 業界別規制の例(監査時に対象へ具体化する): 金融庁の監督指針・ガイドライン、PCI DSS、医薬品規制(CSV)等

#### AIエージェント向け判断基準

**機械判定シグナル:**

| シグナル | 手順 | 判定 |
|---|---|---|
| チケット参照率 | D2-4 の集計を再利用し、直近 6 ヶ月の変更のチケット参照率を算出 | 規制プロファイルで 80% 未満は D12-1 減点(High)。参照先の実在確認は E3 が必要 |
| 逆方向トレース | 直近リリースタグから含まれるコミットを列挙し、参照・承認記録への連鎖を機械的に追う | 追跡が途切れた箇所を具体的に列挙(High)。E3 不在なら「リポジトリ内で可能な範囲」と明記 |
| 時点再現性 | 任意のタグでコード・設定・ロックが揃うか(ロックのコミット状況、設定のバージョン管理状況) | 揃わない要素の列挙は High |
| 方針文書の存在 | データ保持・分類・削除、リリース手続、規制マッピングの文書検出と鮮度 | 不在・12 ヶ月超未更新(規制改定があった場合)は減点根拠(High/Medium) |
| 保持・削除実装 | スキーマ・コード内の保持期限・削除処理の実装痕跡と方針文書の突合 | 「方針あり・実装痕跡なし」は乖離シグナル(Medium — 実装が別リポジトリの可能性) |

**判断留保・エスカレーション:**

- **法令・規制の解釈は行わない**。「要求事項 X に対応する統制が確認できない」という形式で報告し、適合/不適合の結論は有資格者・法務・コンプライアンス部門に委ねる。
- 職務分離・承認の実効性は E3(保護設定・承認記録)なしに判定できない。E1/E2 のみの場合、本領域の多くは NE となる — NE の多さ自体を「監査可能性の所見」として報告する(監査に必要な記録へのアクセスが用意されていないこと自体が統制上の弱点である)。
- 業務証跡の設計妥当性(何を記録すべきか)は業務・規制知識を要する判断的評価。機械判定は「設計文書と実装の対応」の突合までとする。

## 第III部 付録

### 付録A 所見テンプレート

所見は次のフィールドで記録する。Markdown(報告書用)と JSON(集計・追跡用)のどちらで運用してもよいが、フィールドは共通とする。

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | ✓ | 所見 ID(監査内で一意。例: `F-2026-001`) |
| `item` | ✓ | 対応する評価項目 ID(例: `D6-1`) |
| `severity` | ✓ | Blocker / Critical / Major / Minor / Info(3 章) |
| `confidence` | ✓ | High / Medium / Low(7.2 節)。Unconfirmed の場合はその旨 |
| `title` | ✓ | 所見の一文要約(欠陥の内容を述べる。「〜を確認した」ではなく「〜が存在しない/〜が混入している」) |
| `evidence` | ✓ | エビデンス参照の列挙(パス:行、コミット ID、実行コマンドと結果、記録 ID)+ エビデンスクラス(E1〜E4) |
| `impact` | ✓ | 放置した場合に何が起きるか(具体的な失敗シナリオ) |
| `recommendation` | ✓ | 推奨是正(方向性。詳細設計は被監査側の裁量) |
| `due` | ✓ | 是正期限の目安(3 章の重大度既定から調整した場合は理由) |
| `tailoring` | | 関連するテーラリング記録への参照(該当時) |
| `status` | ✓ | Open / In Progress / Resolved / Accepted-Risk(リスク受容には承認者を併記) |

**記入例(様式のみ — 内容はダミー):**

```markdown
### F-YYYY-NNN: <所見の一文要約>
- 項目: Dn-m / 重大度: Major / 確信度: High / 状態: Open
- エビデンス: `path/to/file:123`(E1)、コミット `abc1234`(E2)、実行: `<コマンド>` → <結果要約>
- 影響: <失敗シナリオ>
- 推奨是正: <方向性>
- 期限: YYYY-MM-DD(90 日 — Major 既定)
```

### 付録C 用語集

| 用語 | 定義 |
|---|---|
| 評価領域 | 第II部の D1〜D12。評価の意味論を定義する単位 |
| 評価項目 | 領域内の個別の評価対象(`Dn-m`)。成熟度判定の最小単位 |
| 成熟度(L0〜L4) | プラクティスの定着度の尺度(2 章)。「現在の実力」を表す |
| 重大度 | 所見を放置した場合のリスクの尺度(3 章)。成熟度と独立に管理する |
| 所見(Finding) | エビデンスに基づいて記録された欠陥・リスク・情報(付録A) |
| プロファイル | 対象リポジトリの分類(OSSライブラリ/社内サービス/規制産業システム)。領域重みを決める |
| テーラリング | 対象の性質に応じた評価項目の調整。必ず記録を伴う(8 章) |
| ゲーティング | スコアに優先する総合判定の制約規則(4.4 節) |
| E1〜E4 | エビデンスクラス(5 章): 静的成果物/VCS履歴/プラットフォーム・実行記録/人的・外部 |
| NE(Not Evaluable) | 評価不能。理由付きで記録し、スコア分母から除外(7.6 節) |
| 確信度 | AI エージェントの判定の信頼水準(High/Medium/Low、7.2 節) |
| 要確認(Unconfirmed) | High エビデンスを欠く高重大度所見の区分。人間の検証がブロッキング条件 |
| ホットスポット | 変更頻度が高く、かつ規模・複雑度の大きいコード領域 |
| バス係数 | その人が離脱すると保守が停止する人数。1 が最悪値 |
| フレーキーテスト | 同一コードに対して合否が非決定的に変わるテスト |
| SCA | Software Composition Analysis。依存の既知脆弱性・ライセンスの解析 |
| SBOM | Software Bill of Materials。構成部品表(SPDX/CycloneDX 形式等) |
| 来歴(Provenance) | 成果物がどのソース・環境・手順から生成されたかの検証可能な記録(SLSA) |
